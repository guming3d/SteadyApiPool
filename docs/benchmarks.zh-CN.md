# 性能测试

应用设置的每种网关能承载多少流量、增加多少延迟，以及某个部署故障时客户端看到什么。这些结果于 2026 年
10 月在 Azure 上测得。请把它们当作选择和确定网关规模的参考，而不是保证：你的提示、模型、区域和网络都不同，
请用[规模计算器](getting-started.zh-CN.md#确定网关规模)和[对你自己的后端池做性能测试](getting-started.zh-CN.md#对后端池进行性能测试可选litellm)
来确认你的情况。测试方法以及如何重新测试见 [perf/README.md](../perf/README.md)；每次测试的每一步都在
[perf/results-2026-10/report.md](../perf/results-2026-10/report.md) 中。

## 测试了什么

| 网关 | 规模 | 区域 |
|---|---|---|
| Azure API 管理 基本 v2 | 1 个单元 | 美国中南部 |
| Azure API 管理 标准 v2 | 1 个单元 | 美国中南部 |
| Azure 容器应用上的 LiteLLM | 规模计算器为每分钟 1,800 个聊天请求给出的规模：11–29 个 2 vCPU 副本、PostgreSQL D2ds_v5、Redis B0 | 美国西部 3 |
| AKS 上的 LiteLLM | 规模计算器为每分钟 15,000 个聊天请求给出的规模：8–20 个 D16ds_v5 节点、92–230 个 Pod、PostgreSQL D16ds_v5、Redis B0 | 日本东部 |

每个网关都由应用创建，使用应用自己的后端池设置（APIM：1 次失败触发断路器跳变 60 秒、对 429 重试；LiteLLM：
第一次失败后冷却 60 秒、重试 1 次、超时 120 秒），并由同一区域中的一台虚拟机施加负载。LiteLLM 与 APIM 在不同
区域测试，是因为测试订阅无法在美国中南部创建 PostgreSQL，无法在美国中部、美国东部 2 或西欧创建 Azure
Managed Redis，在美国西部 3 也没有足够的 PostgreSQL vCore；这些结果比较的是网关本身，每个网关的客户端都在
它旁边。

**模型。** 在容量和故障转移测试中，后端池的三个成员是模拟的 Azure OpenAI 部署，像一个固定速度的模型那样
响应（首个 token 在 1 秒加上每 1,000 个提示 token 0.1 秒之后，然后每秒 60 个 token），因此先耗尽的是网关，
而不是模型的配额。真实模型的配额会早得多耗尽；这一部分另外用 gpt-6-luna 测试。

**调用类型。**

| 类型 | 输入 token | 输出 token | 流式传输 | 到最后一个 token 的时间（模拟模型） |
|---|---|---|---|---|
| 简短回答 | 500 | 100 | 否 | 2.7 秒 |
| 聊天 | 2,000 | 500 | 是 | 9.5 秒 |
| RAG | 8,000 | 300 | 是 | 6.8 秒 |
| 代理循环的一步 | 50,000 | 400 | 否 | 12.7 秒 |

**一步通过的条件。** 预热之后，按计划发出负载（开环）2 分钟。一步通过的条件是：失败的请求不超过 1%，
至少处理了 95% 的负载，并且 p95 延迟不超过直接发给模拟模型的同一调用的 1.25 倍。

## 容量

每种网关通过的最高负载（每分钟请求数）。“≥”表示通过了测试的最高一步，实际还能承载更多。

| 类型 | APIM 基本 v2 | APIM 标准 v2 | 容器应用上的 LiteLLM | AKS 上的 LiteLLM |
|---|---|---|---|---|
| 简短回答 | ≥ 22,500 | ≥ 22,500 | ≥ 22,500 | ≥ 15,000 |
| 聊天（流式） | 4,500 | 12,000 | 3,720 | 11,280 |
| RAG（流式） | 2,640 | 5,280 | 5,280 | 14,280 |
| 代理循环的一步 | 10,500 | 16,860 | ≥ 22,500 | ≥ 15,000 |
| 每月标价 | 约 $150（1 个单元） | 约 $700（1 个单元） | 约 $760–5,320 | 约 $8,350–18,580 |

APIM 的月价是单元的价格；超出该层所含调用次数的调用另外计费（按标价，基本 v2 每 10,000 次 $0.03，标准 v2
$0.025），在这样的负载下这部分比单元本身还贵。LiteLLM 的范围从最少的副本或节点到自动缩放器添加的最多数量。

- **流式传输是主要开销。** 每种网关承载的简短回答都是流式聊天的几倍：一个流式回答是几百个小块，每一块都
  要经过网关。代理循环 50,000 个 token 的提示，开销远小于把它的回答流式传回。
- **APIM** 超过容量后逐渐变慢（首个 token 越来越晚），对最大的提示开始让调用失败（5xx）。下一步是增加一个
  单元或改用标准 v2；标准 v2 承载的聊天是基本 v2 的 2.7 倍。
- **容器应用上的 LiteLLM** 承载了它规模的两倍聊天负载（3,720 RPM，规模为 1,800），然后突然失败：在 4,500 RPM
  时调用排队超过 30 秒，部分失败。请用规模计算器按峰值确定规模，它也会告诉你何时该改用 AKS。
- **AKS 上的 LiteLLM** 承载了 11,280 RPM 的聊天（规模为 15,000）和 14,280 RPM 的 RAG。测试中它的 Pod（92 到
  230）和入口（2 到 5 个副本）都扩展了；每一步只有 2 分钟预热，而在流式传输下，入口的 5 个副本可能最先耗尽。
  在你自己做性能测试之前，请以测得的数字而不是规模数字为准。

## 网关增加的延迟

在每分钟 600 个请求时，相比直接发给模拟模型的同一调用，增加的中位数和 p95 延迟（毫秒）：

| 类型 | APIM 基本 v2 | APIM 标准 v2 | 容器应用上的 LiteLLM | AKS 上的 LiteLLM |
|---|---|---|---|---|
| 简短回答 | +6 / +9 | +6 / +13 | +22 / +40 | +22 / +33 |
| 聊天（流式） | +8 / +51 | +5 / +12 | +69 / +195 | +57 / +70 |
| RAG（流式） | +7 / +20 | +6 / +10 | +50 / +88 | +44 / +53 |
| 代理循环的一步 | +9 / +12 | +9 / +14 | +27 / +48 | +26 / +35 |

与 2–13 秒的模型调用相比，两者都很小：APIM 的中位数增加不到 10 毫秒，LiteLLM 增加 20–70 毫秒。接近每种网关的
容量时，p95 会在某一步失败之前增长到一两秒；[完整结果](../perf/results-2026-10/report.md)列出了每一步。

## 部署故障时

在每分钟 1,200 个流式聊天请求下，让模拟的 `mock-a`（后端池的第一个成员）先返回 429 两分钟，然后返回 500，
然后完全不响应，每次之后都有一段正常时间。

| `mock-a` | APIM 基本 v2 | APIM 标准 v2 | 容器应用上的 LiteLLM | AKS 上的 LiteLLM |
|---|---|---|---|---|
| 返回 429 | 0% 失败，立即切换 | 0% | 0% | 0% |
| 返回 500 | 0.08% 失败 | 0.08% | 0% | 0% |
| 恢复 | 60 秒后流量回来 | 60 秒后 | 60 秒冷却后 | 60 秒冷却后 |
| 挂起（从不响应） | 在 120 秒超时后 **99% 失败**（500） | **99.8%** | 0.4% 失败；约 130 秒后才响应 | 0%；约 130 秒后才响应 |

- 返回错误的成员在两种网关上都会立即被移出，客户端察觉不到。
- 接受调用却从不响应的成员，只有在调用超时后才会被发现。在此之前所有调用都发给它：APIM 的重试只针对 429，
  所以这些调用以 500 失败；LiteLLM 会在下一个成员上重试，所以它们成功了，只是晚了两分钟。如果你的调用很短，
  请调低后端池的超时，让挂起的区域代价更小。

## 使用真实模型

同样的调用直接发给一个 gpt-6-luna 部署（每分钟 125 个请求和 125,000 个 token，美国中部），以及通过每种网关
由四个 gpt-6-luna 部署组成的后端池（先美国中部，然后美国东部 2、美国东部 2 DataZone 和瑞典中部 DataZone），
每次都从该网关的虚拟机发出。

负载之所以低，是因为模型的配额。gpt-6-luna 的一个配额单位允许每分钟 1 个请求和 1,000 个 token；第一个部署有
125 个单位，后端池的四个部署合计 450 个，这是测试订阅全部的 gpt-6-luna 配额。调用先达到哪个限制就按哪个算：
每分钟可以有 125 个简短回答，但只有约 3.5 个代理循环的一步，因为它们的提示会占满 token 限制。提示使用的是与
模拟模型测试相同的文本，按每个 token 四个字符确定长度；gpt-6-luna 的分词器计数更少，所以真实调用比类型名称
所说的要小：

| 类型 | 提示 token | 回答 token |
|---|---|---|
| 简短回答 | 359 | 84–87 |
| 聊天 | 1,414 | 415–434 |
| 代理循环的一步 | 35,158 | 281–350 |


| 负载 | 直接发给一个部署 | APIM 基本 v2 | APIM 标准 v2 | 容器应用上的 LiteLLM | AKS 上的 LiteLLM |
|---|---|---|---|---|---|
| 简短回答，每分钟 120 个 | 100% | 100% | 100% | 100% | 100% |
| 简短回答，每分钟 240 个 | 70%（其余 429） | 100% | 100% | 100% | 100% |
| 简短回答，每分钟 360 个 | 35%（其余 429） | 100% | 100% | 100% | 100% |
| 聊天，每分钟 160 个 | 75%（其余 429） | 100% | 100% | 100% | 100% |
| 代理循环的一步，每分钟 8 个 | 44%（其余 429） | 100% | 100% | 100% | 100% |

第一个部署的配额用完后，每个后端池都按顺序由下一个部署、再下一个部署来响应，没有一个调用失败。无论有没有
网关，中位数延迟都是模型本身的（简短回答 1.4–1.8 秒，流式聊天 4–5 秒，首个 token 在 0.85–0.95 秒后）：这些测试
在不同时间进行，它们之间的差别是模型自身的波动，网关增加了多少由上面的模拟模型测试衡量。从日本东部（AKS）
到美国的部署，首个 token 晚了约 0.45 秒。

第一次 LiteLLM 测试发现，对于名称不是其模型名的两个部署（`gpt-6-luna-dz`），LiteLLM 拒绝了 `reasoning_effort`：
它按部署的名称决定一个模型支持哪些参数。应用现在会告诉 LiteLLM 每个 Foundry 部署实际提供的模型（`base_model`，
从部署读取），上面的结果来自修复之后的那次测试。
