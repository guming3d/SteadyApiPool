# 估算 LiteLLM 网关的规模

本文说明如何根据客户的流量估算所需的 LiteLLM 网关：容器应用的副本、PostgreSQL、Redis，或 AKS 的节点和 Pod。
这正是应用中规模计算器（设置中的**部署网关**，`backend/pool_manager/litellm/sizing.py`）所做的计算，这里把它逐步
写出来，方便你理解、手工核对或向客户解释。应用部署的就是规模计算器算出的规模，所以这里的数字就是你实际得到的。

规模只是估算：CPU 数据是实测的，内存是估算值，你的提示和区域也不同。部署后请按峰值
[对后端池做性能测试](getting-started.zh-CN.md#对后端池进行性能测试可选)来确认。

## 需要向客户了解什么

| 输入 | 含义 | 默认值 |
| --- | --- | --- |
| **峰值每分钟请求数（RPM）** | 所有调用方在最繁忙的那一分钟的合计，不是平均值 | （必填） |
| **平均输入 token 数** | 每次调用的提示，包括系统提示、历史记录和工具结果 | （必填） |
| **平均输出 token 数** | 每次调用的回答 | （必填） |
| **超时** | 单次调用最长时间（LiteLLM 的 `request_timeout`） | 120 秒 |
| **流式传输** | 回答是否以流式返回 | 是 |
| 模型速度 | 快、标准或推理模型，或客户自己的平均响应时间 | 标准 |
| 余量 | 峰值之上额外预留 | 25% |
| 区域冗余 | 承受一个可用性区域故障 | 开启 |
| AKS 团队、自托管 GPU 模型、专用网络 | 倾向 AKS 的原因 | 关闭 |

客户给出的往往是**每分钟 token 数（TPM）**而不是 RPM。用每次调用的 token 数换算：

```
RPM = TPM ÷（输入 token + 输出 token）
```

例如，三个智能体各约 15,000 TPM，共 45,000 TPM；每次调用输入 2,000、输出 500 个 token，平均就是
45,000 ÷ 2,500 = **18 RPM**。按峰值估算：如果峰值是平均值的两倍，就填 **36 RPM**。

## 简要结论

- **流式传输决定网关的规模。** 无论调用大小，LiteLLM 每次调用约用 27 毫秒 CPU，但每个流式 token 还要约 0.75 毫秒。
  提示为 2,000 个 token 时，500 个 token 的流式回答约为同样回答非流式返回的 19 倍；提示再大，只要回答不是流式的，
  开销也很小。
- **一个副本**（一个 LiteLLM 工作进程，保持在一个核心的 70%）大约可承载：**非流式约 1,500 RPM**，**流式聊天约 80 RPM**
  （输入 2,000 / 输出 500），流式的 50,000 token 智能体步骤约 **17 RPM**。
- **生产网关至少 2 个副本**（AKS 至少 3 个节点），并配备常规用途的 PostgreSQL 和 Redis，无论流量多小。
- 默认选**容器应用**，除非以下情况：超过 **30 个副本**，调用可能 **240 秒**没有任何输出（非流式且很慢，或首个 token
  就要这么久），客户有 Kubernetes 团队，或要运行自托管 GPU 模型。这些情况选 **AKS**。

常见调用形态所需的容器应用副本数（最少–最多），使用上面的默认值（标准模型、120 秒超时、25% 余量、区域冗余）。
“AKS”表示容器应用被排除，改列 AKS 节点：

| 调用形态（输入 / 输出 token） | 60 RPM | 300 RPM | 1,000 RPM | 3,000 RPM | 10,000 RPM |
| --- | --- | --- | --- | --- | --- |
| 简短回答，500 / 100，流式 | 2 | 2 | 2–5 | 4–11 | AKS：3–7 × D8ds_v5 |
| 聊天，2,000 / 500，流式 | 2 | 2–6 | 7–17 | AKS：4–10 × D8ds_v5 | AKS：6–13 × D16ds_v5 |
| RAG，8,000 / 300，流式 | 2 | 2–6 | 7–17 | AKS：4–10 × D8ds_v5 | AKS：6–13 × D16ds_v5 |
| 智能体步骤，50,000 / 400，流式 | 2–6 | 10–24 | AKS：3–7 × D16ds_v5 | AKS：8–19 × D16ds_v5 | AKS：26–63 × D16ds_v5 |
| 以上任一形态，非流式 | 2 | 2 | 2 | 2–4 | 4–10（50,000 时为 4–11） |

以上都使用 Redis `Balanced_B0`。PostgreSQL 在 33 个副本以内为 `Standard_D2ds_v5`，再多则更大（见[第 7 步](#7-postgresql)）。

## 逐步计算

每一步先给出公式，再以上面的客户（36 RPM，输入 2,000 / 输出 500，流式，其余为默认值）为例。

### 1. 请求和 token

```
每秒请求数     = RPM ÷ 60
每分钟 token 数 = RPM ×（输入 + 输出）
```

每分钟 token 数就是后端池中各 Foundry 部署合计需要的**配额**。网关不会改变它；由多个部署组成的后端池会把它们的配额
加在一起。

> 36 ÷ 60 = **每秒 0.6 个请求**；36 × 2,500 = **90,000 TPM** 的 Foundry 配额。

### 2. 每次调用的时间和同时进行的调用

```
调用时间       = 首个 token + 每 1,000 个输入 token 0.1 秒 + 输出 ÷ 每秒 token 数
同时进行的调用 = 每秒请求数 × 调用时间
拖慢的调用     = 每秒请求数 × 超时      （假如 Foundry 把每个调用都拖到超时）
```

| 模型速度 | 首个 token | 每秒 token 数 |
| --- | --- | --- |
| 快 | 0.5 秒 | 120 |
| 标准 | 1 秒 | 60 |
| 推理模型 | 8 秒 | 40 |

也可以直接填写平均响应时间，它会取代这个公式。

> 1 + 0.2 + 500 ÷ 60 = 每次调用 **9.5 秒**；0.6 × 9.5 = **6 个同时进行的调用**；如果每个调用都用满超时，则为
> 0.6 × 120 = **72 个**。

### 3. 每次调用的网关 CPU，以及一个副本能承载多少

```
每次调用的 CPU = 27 毫秒
              + 每 1,000 个 token（输入 + 输出）0.1 毫秒
              + 流式时：输出 ×（0.75 毫秒 + 每 1,000 个输入 token 0.11 毫秒）

一个副本每秒能承载的请求数 = 700 毫秒 ÷ 每次调用的 CPU
```

700 毫秒是一个 LiteLLM 工作进程（一个核心）保持在 70%；每个副本运行一个工作进程。这些数字是用 `calibrate.py` 在按
本应用部署方式配置的 LiteLLM v1.106.4 上实测的（虚拟密钥、批量写入花费、启用 OpenTelemetry）。0.11 毫秒是
OpenTelemetry 处理每个流式分块的开销，随提示变大而增加。

> 27 + 0.25 + 500 ×（0.75 + 0.22）= 每次调用 **512 毫秒**；700 ÷ 512 = 每个副本**每秒 1.4 个请求**（约 82 RPM）。

### 4. 一个副本的内存能容纳多少调用

```
每个调用的内存 =（输入 + 输出）× 4 字节 × 8 份副本
可容纳的调用   =（内存 × 80% − 1.5 GiB）÷ 每个调用的内存，最多 1,000
```

每个副本有 4 GiB（容器应用和 AKS 相同），即有 1.7 GiB 留给进行中的调用。只有提示非常大、回答又很慢时才会受这一项
限制；大多数流量都是 1,000 的上限。

> 2,500 × 32 = 每个调用 80 KB；1.7 GiB 可容纳 20,000 多个，所以取 **1,000**。

### 5. 副本数

```
负载   = 每秒请求数 ÷ 第 3 步  和  同时进行的调用 ÷ 第 4 步  中较大的一个
峰值   = 负载向上取整（至少 1）
最多   = 峰值 与 负载 ×（1 + 余量）向上取整 中较大的一个，区域冗余时再加 1 个备用
最少   = 峰值的一半向上取整，区域冗余时至少 2 个（否则 1 个），且不超过“最多”
```

最少的副本一直运行，自动缩放最多加到“最多”。关闭区域冗余且一个副本就能承载峰值时，规模只有一个副本，即**开发**
配置（用于试用，没有冗余，使用可突发数据库，没有 Redis）。

> 负载 = max(0.6 ÷ 1.4, 6 ÷ 1,000) = 0.44，所以**峰值 1 个**；最多 = 1 + 1 个备用 = **2 个**；最少 = **2 个**。
> 网关运行 2 个副本，永远不需要更多。

### 6. 容器应用的副本和缩放规则

| | 值 |
| --- | --- |
| 副本 | 2 vCPU、4 GiB（只有一个开发副本时为 1 vCPU、2 GiB），另加 OpenTelemetry Collector 边车容器 0.25 vCPU、0.5 GiB |
| 按同时进行的调用扩展 | 每个副本超过（同时进行的调用 ÷ 峰值副本数）时 |
| 按 CPU 扩展 | 副本分配的 27%，即其唯一工作进程一个核心的 60%（60 × 1 ÷ 2.25） |
| 限制 | 每个规模最多 30 个副本；入口会结束 240 秒没有任何输出的请求 |

60% 低于副本按 70% 估算的目标，所以新副本（启动需要几分钟）会在其他副本饱和之前到位。

> 2 个 2 vCPU / 4 GiB 的副本；每个副本超过 6 个同时进行的调用或 27% CPU 时扩展。

### 7. PostgreSQL

```
连接数 = 最多副本数 × 10（LiteLLM 每个副本的连接池）× 2（更新时新旧版本同时运行）
```

规模取连接数（按 80% 计）足以容纳的最小常规用途服务器：

| 服务器 | 连接数（80%） | 最多 |
| --- | --- | --- |
| `Standard_B1ms`（可突发） | 35 | 仅限单个开发副本 |
| `Standard_D2ds_v5` | 844（675） | 33 个副本 |
| `Standard_D4ds_v5` | 1,703（1,362） | 68 个副本 |
| `Standard_D8ds_v5` | 3,422（2,737） | 136 个副本 |
| `Standard_D16ds_v5` | 4,985（3,988） | 199 个副本 |

超过 199 个副本时仍用 D16ds_v5，但会降低 LiteLLM 每个副本的连接池（并给出警告）；每个副本不足 2 个连接时（约 1,000 个
副本）会拒绝，并建议把流量分到更多网关。多于一个副本时不用可突发：它在持续负载下会耗尽 CPU 积分。

> 2 × 10 × 2 = 40 个连接：**`Standard_D2ds_v5`**。

### 8. Redis

| 峰值每秒请求数 | Azure 托管 Redis |
| --- | --- |
| 只有一个副本 | 不需要 |
| 不超过 1,000 | `Balanced_B0` |
| 不超过 2,500 | `Balanced_B1` |
| 不超过 5,000 | `Balanced_B3` |
| 更多 | `Balanced_B5` |

Redis 让各副本共享冷却状态和计数。每秒 1,000 个请求或 10 个副本起，花费也通过 Redis 写入
（`use_redis_transaction_buffer`，LiteLLM 的建议）。

> 2 个副本、每秒 0.6 个请求：**`Balanced_B0`**，花费直接写入数据库。

### 9. AKS 节点和出站端口

在 AKS 上每个副本就是一个 1 vCPU、4 GiB 的 Pod（请求和限制相同），所以 Pod 数就是第 5 步的副本数。节点：

| 节点 | 每个节点的 Pod |
| --- | --- |
| `Standard_D4ds_v5` | 2 |
| `Standard_D8ds_v5` | 5 |
| `Standard_D16ds_v5` | 12 |

```
节点大小 = 使（最多 Pod ÷ 每个节点的 Pod）不超过 10 个节点的最小规格（否则 D16ds_v5）
最多节点 = 最多 Pod ÷ 每个节点的 Pod，向上取整，区域冗余时至少 3 个
最少节点 = 最少 Pod ÷ 每个节点的 Pod，向上取整，区域冗余时至少 3 个
层       = 区域冗余时为标准层，否则为免费层
```

超过 100 个节点会被拒绝：请把流量分到更多区域的网关。如果订阅在该区域不能使用 Ddsv5 系列，则依次改用 Ddsv7、Ddsv6
中相同大小的规格。

**出站端口。** 每个对 Foundry 的调用在运行期间占用一个 SNAT 端口。每个节点需要足够的端口来承担第 2 步中拖慢的调用：

```
每个节点的端口 = 拖慢的调用 ÷ 峰值时的节点数
出站 IP       = 足以让（最多节点 + 1 个升级用节点）× 每个节点的端口 放进每个 IP 的 64,000 个端口，最多 16 个
```

如果 16 个 IP 仍然不够，规模会给出警告：只有 Foundry 慢到这种程度时，调用才需要等待端口。

**超时。** AKS 上的路由允许一次调用加一次重试：600 秒与（超时 × 2 + 60 秒）中较大的一个。

> 2 个 Pod：**3 × `Standard_D4ds_v5`**（3 个用于跨可用性区域，运行 2 个 Pod），标准层；72 个拖慢的调用分到 3 个节点，
> 每个节点 24 个端口，1 个出站 IP，每个节点 16,000 个端口。

### 10. 容器应用还是 AKS

满足以下任一条件时，规模计算器推荐 **AKS**，否则推荐**容器应用**：

| 原因 | 说明 |
| --- | --- |
| 非流式，且超时（或调用时间）超过 240 秒 | 容器应用的入口会结束 240 秒没有任何输出的请求（实测：241 秒收到 504） |
| 流式，但首个 token 可能在 240 秒之后才到 | 同上；token 开始输出后，流式调用可以运行更久 |
| 最多副本数超过 30 个 | 容器应用的规模上限 |
| 客户已在运维 AKS，或要运行自托管 GPU 模型 | 客户对平台的选择 |

专用网络在两者上都可以实现，但没有自动化：在容器应用上，之后把环境放进虚拟网络；在 AKS 上，使用内部负载均衡器或
专用入口。

容器应用的高级入口可以把 240 秒提高到 30 分钟，但需要一个至少两个节点、一直计费的专用工作负载配置文件。本应用不会
配置它，规模计算器也仍按 240 秒计算。

> 流式，首个 token 在 1.2 秒后到达，2 个副本：**容器应用**。

## 计算示例

都使用标准速度的模型、25% 余量和区域冗余。

| | 客户的智能体 | 聊天 | 大规模聊天 | 推理智能体 |
| --- | --- | --- | --- | --- |
| 峰值 | 36 RPM | 1,800 RPM | 15,000 RPM | 300 RPM |
| token（输入 / 输出） | 2,000 / 500 | 2,000 / 500 | 2,000 / 500 | 20,000 / 2,000 |
| 流式、超时 | 是，120 秒 | 是，120 秒 | 是，120 秒 | **否**，600 秒，推理模型 |
| 需要的 Foundry 配额 | 90,000 TPM | 450 万 TPM | 3,750 万 TPM | 660 万 TPM |
| 调用时间、同时进行的调用 | 9.5 秒，6 个 | 9.5 秒，286 个 | 9.5 秒，2,384 个 | 60 秒，300 个 |
| 每次调用的 CPU、每个副本 | 512 毫秒，82 RPM | 512 毫秒，82 RPM | 512 毫秒，82 RPM | 29 毫秒，1,440 RPM |
| 副本（最少–最多） | 2–2 | 11–29 | 92–230 | 2–2 |
| **推荐** | **容器应用** | **容器应用** | **AKS**（超过 30 个副本） | **AKS**（超过 240 秒无输出） |
| 容器应用 | 2 × 2 vCPU / 4 GiB | 11–29 × 2 vCPU / 4 GiB | 不适用 | 不适用 |
| AKS | 3 × D4ds_v5 | 3–6 × D8ds_v5 | 8–20 × D16ds_v5 | 3 × D4ds_v5 |
| PostgreSQL | D2ds_v5 | D2ds_v5 | D16ds_v5（连接池降为 8） | D2ds_v5 |
| Redis | B0 | B0，花费通过 Redis 写入 | B0，花费通过 Redis 写入 | B0 |

聊天和大规模聊天正是[基准测试](benchmarks.zh-CN.md)中测过的两种规模：容器应用网关按 1,800 RPM 估算，实际承载了
**3,720 RPM** 的流式聊天；AKS 网关按 15,000 RPM 估算，实际承载了 **11,280 RPM**。所以容器应用的规模有富余；规模很大的
AKS，在你自己做过性能测试之前，请以实测数字为准。

## 规模不包括的内容

- **Foundry 配额。** 网关承载的流量不会超过后端池中各部署的配额。第 1 步的每分钟 token 数是后端池合计需要的配额；后端池
  会把它分到多个部署上，并在某个部署返回 429 时故障转移。
- **价格。** 部署表单会按你选择的区域为这个规模计算标价（零售标价，从最少到最多的副本或节点）。部署后，网关面板会显示
  本月的实际花费。
- **区域容量。** 部署表单会在创建任何资源之前，检查该区域是否提供每种资源，以及订阅是否有足够配额。
- **流量变化。** 网关面板中的**按新的流量调整规模**会为本应用部署的网关重新计算规模，并在你确认后应用。

## 自己运行规模计算器

在应用中：设置中的**部署网关**，然后在每个平台的卡片上打开**计算过程**。

在终端中，不需要 Azure（在 `backend/` 中运行）：

```sh
.venv/Scripts/python -c "from pool_manager.litellm import sizing; from pool_manager.litellm.models import GatewaySizing; print(sizing.plans(GatewaySizing(peak_rpm=36, input_tokens=2000, output_tokens=500, timeout_seconds=120, streaming=True)).model_dump_json(indent=2))"
```

`GatewaySizing` 还接受 `model_speed`（`"fast"`、`"standard"`、`"reasoning"`）、`response_seconds`、
`headroom_percent`、`zone_redundant`、`kubernetes_team`、`self_hosted_models` 和 `private_network`。结果包含两个平台
的规模、上面的每个数字，以及应用显示的提示。
