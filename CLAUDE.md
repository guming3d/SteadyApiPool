# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**SteadyApiPool** (repository `guming3d/SteadyApiPool`, formerly `apim-backend-pool-manager`): a standalone manager for Azure API Management **native backend pools** (Single member backends, Pool backends, binding a pool to an API via policy, and discovering Azure OpenAI/Foundry deployments to import as members). Its defaults (circuit breaker, retry, priorities) and ARM body shapes are deliberate; keep them unless a change asks for it. FastAPI backend + React/Vite frontend, deployed to App Service with `azd`.

The older names stay where something depends on them, so don't rename these to SteadyApiPool: the policy markers `<!-- apim-backend-pool:… -->` (`policy.py`, `policy-diff.ts`), `MANAGED_MARKER` ("Managed by APIM Backend Pool Manager."), the `managed-by: apim-backend-pool` tag (`MANAGED_TAG_VALUE`), the custom role names `APIM Backend Pool Manager` / `APIM Backend Pool Deployment Reader` (looked up by `access.py`) and the `guid()` seeds in the Bicep, the `apim-backend-pool:` storage keys, the MSAL cache name `apim-backend-pool` in `credentials.py`, and the default `apimPublisherName` (changing it would update an existing APIM service).

## Commands

Backend (run from `backend/`; on Windows the venv uses `.venv/Scripts/`, on POSIX `.venv/bin/`):

```sh
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt pytest==9.1.1 ruff==0.15.22 mypy==2.3.0
cp .env.example .env                                   # POOL_MANAGER_* settings; APIM is chosen in the app
.venv/Scripts/python -m uvicorn pool_manager.app:app --reload   # :8000
.venv/Scripts/python -m pytest -q
.venv/Scripts/python -m pytest -q tests/test_app.py::<test_name>  # single test
.venv/Scripts/python -m ruff check . && .venv/Scripts/python -m ruff format --check .
.venv/Scripts/python -m mypy                           # strict, configured in pyproject.toml
```

Both servers at once, with prerequisite/`.env` checks and installs only when needed: `scripts/start-local.ps1` (Windows; `start-local.cmd` bypasses the execution policy) or `scripts/start-local.sh`. They first run `scripts/doctor.py --brief` (`-SkipChecks` / `--skip-checks` to skip). Without Node.js 22+ (or with `-Prebuilt` / `--prebuilt`) they skip Vite and the backend serves the built UI on :8000.

Frontend (run from `frontend/`):

```sh
npm ci
npm run dev        # :5174, proxies /api to :8000 (override with API_PROXY_TARGET)
npm test           # node --test tests/*.test.mjs (imports src/*.ts directly)
node --test --test-name-pattern "<name>" tests/pool-modes.test.mjs   # single test
npm run typecheck
npm run build      # outputs to ../backend/pool_manager/static
```

Terminal UI (run from `tui/`; its tests import the backend, so install both requirement sets):

```sh
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt -r ../backend/requirements.txt pytest==9.1.1 ruff==0.15.22 mypy==2.3.0
.venv/Scripts/python -m pool_tui                       # reuses :8000 or starts backend/ itself; --api URL
.venv/Scripts/python -m pytest -q                      # tests/test_tui_app.py drives the app headless
.venv/Scripts/python -m ruff check . && .venv/Scripts/python -m mypy
```

`scripts/start-local.ps1 -Tui` / `start-local.sh --tui` run the backend plus the TUI instead of the browser frontend.

`backend/.venv/Scripts/python scripts/demo_server.py` serves the built UI on :8010 against `tests/fake_apim.py` (no Azure; the real credential factories refuse to build). `POST /demo/stage/{sign-in,ready,pool}` resets it to a point in onboarding. The README's Get started screenshots in `docs/images/` come from it; retake them when the UI they show changes.

Environment preflight and release: `python scripts/doctor.py` (stdlib only, Python 3.8 syntax so it can say "too old" on old Pythons; per-OS install commands, Node/prebuilt decision, sign-in tools, headless/SSH/WSL, keyring, DNS/TLS/proxy to Entra, ARM and the package indexes; tests in `backend/tests/test_doctor.py`). `python scripts/package-release.py` zips backend (with `static/`), tui, the scripts and README into `dist/`, which needs Python only; `.github/workflows/release.yml` publishes it on `v*` tags. `.gitattributes` pins `*.sh` to LF so WSL can run a Windows checkout.

Infra: `az bicep build --file infra/main.bicep --stdout > /dev/null`. Deploy: `azd provision --preview`, then `azd up`. The `prepackage` hook in `azure.yaml` builds the frontend into the backend package.

The public app has its own azd project: `cd deploy/container-apps && azd up` (Bicep in `deploy/container-apps/infra`, `az bicep build --file deploy/container-apps/infra/main.bicep --stdout > /dev/null`). It builds the repo-root `Dockerfile` in ACR (`remoteBuild`), and its `preprovision`/`postprovision` hooks run `scripts/public-app-registration.py` (stdlib + `az`; tests in `backend/tests/test_public_app_registration.py` against an in-memory Graph), which creates the multi-tenant app registration and adds the redirect URI and federated credential. Never run those hooks against a real tenant without being asked: they write to Entra.

CI (`.github/workflows/ci.yml`) runs ruff check, `ruff format --check`, mypy and pytest for the backend and the TUI, `npm test`, `npm run build` and the Bicep build. Run the same before you consider a change done.

**Local dev uses your Azure identity (the setup wizard's browser or device-code sign-in, or `az` / `azd` / Azure PowerShell) against a real APIM service. Writes are live.** Tests don't need Azure.

## Architecture

**Single origin.** FastAPI serves the JSON API under `/api` and the built SPA from `backend/pool_manager/static` (a catch-all route in `app.py`). Same origin is required for the Easy Auth cookie and the CSRF header check. `static/` is build output and is gitignored.

**Backend layering** (`backend/pool_manager/`):
- `app.py`: routes only. Routes that work on the APIM service sit on the `bound` router, which answers 409 until a service is chosen. Dependencies come from `deps.py` (`get_arm`, `get_service`, `get_discovery`, `get_access`, `get_targets`, `get_tester`, `get_monitor`, `get_cost`, plus `get_user`, `get_verifier`, `get_sessions` for the public app) and `config.get_settings`; `app.py` re-exports them and tests replace them through `app.dependency_overrides` (see `tests/test_app.py::_client`, `tests/test_public.py::_Public`). Locally and with Easy Auth each `get_*` returns a process-wide `lru_cache` singleton (`_arm`, `_service`, ...); in the public app it returns the caller's session's component. Routes read settings through `get_request_settings` (the session's, with the chosen service, in the public app). `GET /api/config` is unauthenticated and tells the browser which mode it is in. A `ServiceError` becomes a JSON error with its status code.
- `service.py` (`PoolManagerService`): all APIM operations and the safety rules. It translates `ArmError` into `ServiceError`.
- `arm.py` (`ArmClient`): a small httpx ARM client scoped to the one APIM service. Paths are relative to the service, `""` is the service itself, and `segment()` escapes path parts. It handles retries/backoff and takes an injectable credential, transport and sleep.
- `resources.py`: builds ARM request bodies (Single/Pool backends, circuit breakers) and parses readbacks into views.
- `policy.py`: edits API policy XML via marker comments (`<!-- apim-backend-pool:inbound:begin -->` …). It only rewrites its own blocks. The original `<backend>` section is base64-encoded into the marker so unbinding restores the policy **byte for byte**. It raises `PolicyConflict` when a policy's backend section isn't simple enough to take over.
- `config.py` / `target.py` (`TargetChooser`): the APIM service. Set in the environment (`POOL_MANAGER_SUBSCRIPTION_ID`, `_RESOURCE_GROUP`, `_APIM_NAME`, all or none) it is fixed; the deployed app requires it. Locally without it, the setup wizard lists tenants, subscriptions and services, or creates a service, and saves the choice to `backend/.pool-manager.json` (with its tenant, so tokens are requested there). `get_settings` merges that file in and `deps.reset_target` rebuilds every service-bound factory after a switch, keeping the local credential.
- `api_test.py` (`ApiTester`): the call guide's key step and test call. Keys (APIM subscriptions) are listed, created and read with the **user's** ARM client (`AccessChecker.require_user`), never the app identity. The test call goes from the backend to this service's gateway because the gateway sends no CORS headers.
- `metrics.py` (`PoolMonitor`): the pool's Monitor tab, read-only Azure Monitor metrics with a one-minute cache. APIM metrics have no backend dimension, so pool numbers come from the bound APIs (`ApiId`); per-member numbers come from each Foundry deployment's Azure OpenAI metrics (`ModelDeploymentName`, `interval=FULL`) and include callers outside the pool. Needs `Microsoft.Insights/metrics/read` (in both custom roles); a 403 becomes a message on the tab, never a setup blocker.
- `cost.py` (`CostReader`): the service panel's cost. This month's spend is a Cost Management query (`ActualCost`, `MonthToDate`) on the service's resource group filtered to its resource ID, sent with the **user's** ARM client (`access.user_arm`), so the app identity gets no billing access and no role change; it is cached an hour per caller. The list price comes from the public Retail Prices API (`prices.azure.com`, no token ever sent there): the `<tier> Unit` hourly price × units × 730, plus the `<tier> Calls` overage, cached a day per region. A missing token, a 403 or an unsupported subscription becomes `month_to_date_note`, never an error.
- `discovery.py`: scans Cognitive Services accounts across the discovery subscriptions (thread pool, 5-minute cache) and imports deployments as members using managed identity auth.
- `model_deploy.py` (`ModelDeployer`): the Deployments tab's **Deploy a model**. Lists an account's deployable OpenAI models (`accounts/{a}/models`), the quota left (`locations/{loc}/modelCapacities`) and creates deployments, all with the **user's** ARM client. It is built per request in `app.py` from the request's `Discovery`, so there is no `deps.py` factory to override.
- `models.py`: strict Pydantic models (`extra="forbid"`) shared by the API. `frontend/src/types.ts` mirrors them by hand, so keep the two in sync.
- `auth.py`: identity comes from the Easy Auth `X-MS-CLIENT-PRINCIPAL-*` headers. Writes need the `X-Pool-Manager: 1` header, which is the CSRF defence, **and** either the principal in `POOL_MANAGER_OWNERS` or (with `rbac_writers`) the user's own ARM token allowing every APIM read/write the app makes. `frontend/src/api.ts` adds that header to every non-GET request. `auth_mode=disabled` is for local dev only and is rejected when `WEBSITE_SITE_NAME` or `CONTAINER_APP_NAME` is set (Azure hosting). In the public app (`auth_mode=entra`) the principal is the verified Entra user, `can_write` is always true (Azure decides), and the `X-MS-*` headers are never read, since a client could forge them.
- `entra.py` (public app): `TokenVerifier` checks the browser's bearer token (Entra JWKS via PyJWT, audience `<client id>`/`api://<client id>`, issuer `https://login.microsoftonline.com/<tid>/v2.0` matching the token's own `tid`, the `access_as_user` scope, `entra_allowed_tenants`). `OboExchanger` is a plain OBO token request whose client assertion comes from the user-assigned managed identity (federated credential; no secret), and maps Entra's consent errors to `SignInRequired(code="ConsentRequired")`. `UserCredential` is the per-user token credential `ArmClient` uses; it holds ARM tokens in memory only and refuses other tenants (`TenantMismatch`).
- `sessions.py` (public app): `Sessions` builds one `UserSession` (the same components as locally: ARM client, service, discovery, monitor, tester, cost, access, targets) per verified `(tid/oid, target)`, for the service in the `X-Pool-Manager-Target` header (`<sub>/<rg>/<name>`, URL-encoded; `parse_target`). That is the isolation between users: every cache lives in one user's session. Sessions end on idle (`session_idle_seconds`), LRU when full (`max_sessions`, at most 8 per user), or `POST /api/session/sign-out`; a user's credential goes with their last session. It also rate-limits per user (`user_requests_per_minute`). The guest view (`guest_*` settings, `Settings.as_guest`) is one shared session for visitors who send `X-Pool-Manager-Guest: 1` and no token (`deps.get_guest`): it reads the configured service with the app's managed identity (built-in Reader on that subscription, `deploy/container-apps/infra/modules/guest-reader.bicep`), its principal has `guest: true` and `can_write: false`, and `acting_user`, `writer`, `AccessChecker.require_user` and the target chooser refuse it, so it can change, reveal (keys, test calls) or choose nothing. Guests are rate-limited per client address and in total.
- `access.py` (`AccessChecker`): the setup wizard. Builds `SetupReport` from `Microsoft.Authorization/permissions` (effective permissions, matched with wildcards and `notActions`) and APIM identity role assignments, whose role definitions it reads instead of hard-coding role IDs. It performs the fixes. While a report runs it records, per caller, which step it is on; `GET /api/setup/progress` returns that without calling ARM, and the frontend's `components/startup-progress.tsx` polls it in place of a bare "Loading" (keep its step kinds in step with `SetupStepKind`). Three identities: the *operator* (app MI deployed, `az login` locally) does pool work; the *user* (`user_token()` from Easy Auth's `X-MS-TOKEN-AAD-*` headers when deployed, the operator locally) runs fixes; APIM's own MI needs an inference role on Foundry accounts. `credentials.py` (`LocalCredential`) is the local credential: the app's own sign-in (browser, or device code in a background thread for machines without a browser) first, then Azure CLI, azd and Azure PowerShell, skipping a tool that missed for 60 s (`forget_misses` on re-check). App sign-ins are remembered through MSAL's encrypted cache (`CACHE_NAME`) plus an account record in `backend/.pool-manager-auth.json`; with no OS encryption (Linux/WSL without libsecret) they stay in memory, never plaintext. `SetupReport.local_sign_in` reports the source and whether it is remembered. Locally, `config.system_trust` makes the lifespan inject `truststore`, so TLS uses the OS certificate store.

**Invariants to preserve when changing service logic:**
- Creating an APIM service (local setup only) uses the signed-in user's own rights, checks the name first, creates with `If-None-Match: *` and tags it `managed-by: apim-backend-pool`. It may register the `Microsoft.ApiManagement` provider and create a missing resource group, but never changes an existing service or resource group. Consumption is not offered (no circuit breaker).
- Deleting an APIM service (local setup only, `TargetChooser.delete`) is limited to services carrying that `managed-by` tag, needs the name typed again (checked by the backend, not just the UI), and soft-deletes: Azure keeps the service 48 hours and `restore` (PUT with `properties.restore: true`) brings it back. The app never purges and never deletes resource groups. Deleting the current service clears `backend/.pool-manager.json` so setup asks again.
- Every update is ETag-conditional (`If-Match`, or `If-None-Match: *` on create).
- The public app stores nothing server-side: no tokens beyond the in-memory session, no state file (`TargetChooser` never calls `save_target` there; the browser keeps the choice), no secret (federated credential only). Sessions are keyed by the verified tenant and object ID only. Its settings refuse a fixed APIM service or `discovery_subscriptions`, since nothing may be shared between users. Its test call only goes to Azure's gateway host names (`AZURE_GATEWAY_SUFFIXES`, no explicit port). It sends a Content-Security-Policy (inline scripts by hash, Entra only for connect/frame/form), and only `/redirect.html` may be framed (same origin), for MSAL's silent renewal.
- Subscription keys are read only for subscriptions whose scope opens the API being tested, never the built-in `master` one, and never logged or stored. The only subscription the app writes is one test subscription per API (`<id_prefix>test-<api>`, scoped to that API, `If-None-Match: *`). The test call only POSTs below the path of an API bound to a pool, on this service's HTTPS gateway, and returns a filtered set of response headers (no cookies).
- Resources whose IDs start with a protected prefix (`POOL_MANAGER_PROTECTED_PREFIXES`, empty by default; e.g. `finops-` for resources another tool manages) are read-only.
- Members still in a pool can't be deleted, and `DELETE /pools/{id}` refuses a pool still bound to an API. Removing a pool together with its APIs, and the service-wide cleanup, go through a read-only plan (`GET /pools/{id}/removal`, `GET /cleanup`) and then `POST` the plan the user reviewed (`RemovalConfirm`; cleanup also needs the service name typed again). `_remove` recomputes the plan and refuses to delete or unbind anything the user didn't see. It unbinds other APIs first (restoring their policy), then deletes the APIs this app created for the pools, the pools, and the members no remaining pool uses (`_delete_orphans`). Cleanup takes only pools this app created (`managed`) and leaves the service itself.
- Members are managed inside their pool; there is no backends page. When a pool save drops members, or a pool is deleted, `_delete_orphans` deletes the Single backends this app created (`MANAGED_MARKER`) that no pool uses any more, with the credential named value made for them. It never touches other backends, and a failed cleanup is logged, not raised. Importing deployments on their own (without a pool) is not offered, so imports always land in a pool.
- The circuit breaker is a pool setting (`PoolWrite.circuit_breaker`). A save writes it, ETag-conditionally, to each member this app manages whose rule differs (`_apply_breaker`); backends this app didn't create keep theirs. Omitting it leaves members as they are. `frontend/src/pool-breaker.ts` (ported in `tui/pool_tui/logic.py`) derives the rule a pool starts from and which members a publish rewrites.
- Every pool save runs `model_check.py`: members pointing at a Foundry deployment must serve the same model, read from the deployment's ARM resource (never from a name). Members whose model can't be read fail. `POST /api/pools/model-check` is the read-only version the editor uses.
- Backends created here carry `MANAGED_MARKER` at the start of their description. Single backends without it are treated as read-only.
- APIs created for pools (`create_pool_api`) carry the same marker. The app only creates APIs (`If-None-Match: *`) or finishes one it created earlier for the same pool and path. It deletes an API only when it carries the marker (checked again right before the ETag-conditional DELETE) and its pool is being removed; `api_pool_id` reads which pool it was created for. It never modifies or deletes other APIs.
- Deploying a model runs with the user's own ARM token (`require_user`), never the app identity, so the app's Foundry role stays read-only. Only accounts the discovery scan finds take a deployment; the model, version, deployment type and capacity are checked against that account's `models` list before the PUT, and an existing deployment name is never replaced. Only OpenAI-format models and the pay-per-token types (GlobalStandard, DataZoneStandard, Standard) are offered: partner models such as Anthropic use other APIs that pools can't front yet, and provisioned (PTU) is a costly commitment. Fine-tune SKUs in the models list are skipped.
- Pool reads and writes use `pool_api_version` (preview by default) because GA `2024-05-01` drops `pool.sessionAffinity`. Everything else uses `api_version` (GA).
- Setup fixes run with the **user's** token, never the app identity, and the app identity never gets `roleAssignments/write`. Grants are limited to *Cognitive Services OpenAI User* for APIM's managed identity on accounts that are pool members or discovered (`grant_foundry_access` refuses others), with deterministic assignment names so retries are idempotent. Fix endpoints need the CSRF header and sign-in but not the owners list, because Azure itself authorizes them.

**Tests.** `backend/tests/test_public.py` covers the public app with RSA-signed test tokens, the real verifier and session store, and a fake exchange that gives each user their own ARM token in `FakeApim.callers` (isolation, sign-out, idle expiry, rate limit, CSP, gateway hosts, OBO request shape). `backend/tests/test_app.py` drives the real app through `TestClient`, with `ArmClient` wired to `tests/fake_apim.py`. That file is an in-memory APIM behind `httpx.MockTransport`. It enforces ETags and conditional headers and records requests so tests can assert on API versions and headers. It also maps bearer tokens to callers (`callers`), serves effective permissions per caller and scope (`allow()`; a caller without entries has full access), role assignments and definitions, and the unauthenticated tenant challenge. `tests/test_setup.py` covers the wizard in local and deployed modes. `tests/test_target.py` covers choosing and creating the service, `tests/test_api_test.py` the keys and the test call (with a mocked gateway), and `tests/test_metrics.py` the dashboard (`FakeApim.add_metric` serves Azure Monitor series, filtering on `X eq 'v'` and splitting on `X eq '*'`); the fake also serves tenants, subscriptions, resource groups, other APIM services (`add_service`), provider registration and APIM SKUs, and for Deploy a model each account's `models` list (`account_models`), free capacity (`capacities`) and deployment creates (a new deployment reads `Creating` once, then `Succeeded`; `deploy_forbidden` and `deploy_error` simulate refusals). When you add an ARM call, extend the fake to match. `tests/conftest.py` makes any test that reaches the real ARM factories in `deps.py` fail, because a missed override would otherwise sign in with the developer's own Azure identity; `_client` overrides `get_targets` as well, with a throwaway state file.

**Frontend** (`frontend/src/`): TanStack Query. The query definitions and the fetch wrapper are in `api.ts`. `main.tsx` first runs `session.ts`'s `startSession` (reads `/api/config`); in the public app it loads MSAL.js lazily (`@azure/msal-browser`, tokens in `sessionStorage`, every flow returning through `redirect.html` / `src/redirect-bridge.ts`, a second Vite entry), shows `components/sign-in-page.tsx` until the user signs in, and registers `configureRequests` so every API call carries the bearer token and the `X-Pool-Manager-Target` header. The chosen service is kept per account in `localStorage` (pure helpers in `public-target.ts`); `apim-picker.tsx` and `setup-wizard.tsx` call `chooseTarget` and use MSAL for sign-in and consent there, and the top bar shows **Sign out**. There are two tabs (pools, deployments) in `app.tsx`, and the tab is kept in `?tab=` (an old `?tab=backends` lands on pools). A pool's members, including custom non-Foundry endpoints (`components/member-backend-dialog.tsx`, added from the members picker), and its circuit breaker (`components/pool-breaker-settings.tsx`, in the pool's Settings) are edited inside the pool editor. Removing a pool and cleaning up the service (`components/removal-dialog.tsx`, confirm payload in the pure `removal.ts`) show the backend's plan and confirm exactly it; the cleanup and the service delete (`DeleteServiceDialog`, shared with the APIM picker) open from `components/service-panel.tsx`, behind the APIM name in the top bar. `components/setup-wizard.tsx` is the setup wizard (auto-opened once per session when something needs attention, full page when `can_operate` is false), plus `FoundryAccessNotice`, used in the Deployments selection bar and the call guide; step grouping lives in the pure `setup-steps.ts`. Pool mode logic (failover/balanced/weighted derived from member priority and weight, plus validation and payload building) lives in the pure module `pool-modes.ts` so `node --test` can test it. The Monitor tab (`components/pool-monitor.tsx`, arithmetic in the pure `pool-metrics.ts`) draws its own SVG charts; its colours are CSS variables on `.monitor` with separate dark steps, checked with the dataviz palette validator. The first-run guided tour is `components/product-tour.tsx` with its steps in the pure `tour-steps.ts`; steps point at elements by `data-tour` attributes, so keep those when moving or renaming the elements they mark, and keep the tour copy naming the real button and tab labels. Colours, corners, shadows and the overlay are tokens on `:root` in `styles.css` (the Azure theme); dark mode overrides them on `:root[data-mode="dark"]`, never through `prefers-color-scheme`, because the top-bar toggle (`components/theme-toggle.tsx`, pure logic in `theme.ts`, first paint in an inline script in `index.html`) can override the OS. Use tokens rather than literal colours or radii, and keep every text colour at 4.5:1 or better on `--card` and `--muted` in both modes. All UI strings live in `i18n.tsx`. Chinese (`zh`) is the source; its Azure terms follow the official zh-cn APIM docs on learn.microsoft.com (断路器 and 跳变 / 跳变持续时间, 托管标识, 会话感知, 运行状况, 故障转移 / 轮询 / 加权, 终结点, 速率限制, 开发人员层), so check new copy against them. `en` is typed as `Record<keyof typeof zh, string>`, so any new key has to be added to both.

**Terminal UI** (`tui/pool_tui/`): a Textual app that is only a client of `/api` (`client.py`, async httpx, adds the `X-Pool-Manager` header on writes), so it must never reimplement a backend rule. `logic.py` ports `pool-modes.ts`, `pool-metrics.ts` and `api-test.ts`; keep them in step with the web UI, as with `types.ts`. Views are `views/` (pools, deployments, setup, switched with 1-3) and modals are `screens/`; the Omarchy look is `theme.py` (registered in `App.__init__`, before the stylesheet is parsed) plus `app.tcss`. `backend.py` reuses a backend on :8000 or starts `backend/` from its venv, logging to a temp file. `tests/conftest.py` wires the real FastAPI app to `backend/tests/fake_apim.py` through `httpx.ASGITransport`, and `tests/` has no `__init__.py`, so `tests.*` imports resolve to the backend's test package.

**Public app infra** (`deploy/container-apps/infra/`): Container Apps (external ingress on 8000, min 1 replica), ACR (AcrPull for the user-assigned identity, no admin user), Log Analytics, and that identity, which is also the app registration's federated credential and has no other Azure role. `modules/current-image.bicep` keeps the deployed image across re-provisions (`SERVICE_WEB_RESOURCE_EXISTS`). Its outputs feed the postprovision hook.

**Infra** (`infra/`): `main.bicep` creates the App Service with Easy Auth, then assigns least-privilege custom roles. With `apimName` empty it also creates an APIM service (`modules/apim.bicep`, `BasicV2` by default) in the same resource group. `enableDelegatedAzureAccess` (off by default, because sign-in breaks until the app registration steps in README are done) adds the ARM `user_impersonation` scope to Easy Auth and a user-assigned identity used as its federated credential. `modules/apim-rbac.bicep` covers the backends, named values and API policies on the APIM service, plus `apis/write` and `apis/operations/write` for creating pool APIs. `modules/discovery-rbac.bicep` gives read-only Cognitive Services access per discovery subscription and has no `listKeys`. If the app starts calling a new ARM action, add it to the matching custom role.
