# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**SteadyApiPool** (repository `guming3d/SteadyApiPool`, formerly `apim-backend-pool-manager`): one app that puts an AI gateway with failover in front of Azure OpenAI / Foundry deployments, for people who know neither the gateway nor Foundry. The user chooses the kind of gateway (the *product*) on the setup page:

- **`apim`**: Azure API Management **native backend pools** (Single member backends, `Pool` backends, a pool API bound through policy, session affinity). Uses an existing APIM service or creates one.
- **`litellm`**: a **LiteLLM gateway** (a pool is a LiteLLM model group). Deploys it on Azure Container Apps in one step, or on a new AKS cluster it installs LiteLLM on and then hands over, or gives the files for an existing cluster, or connects any LiteLLM proxy with a database.

Both discover Foundry deployments, group deployments of one model into pools with failover, weights and breaker/cooldown, give a call guide with a test key and a test call, and a Monitor tab. Their defaults (APIM: circuit breaker on 1 failure for 60 s, 2 retries; LiteLLM: cooldown on the first failure for 60 s, 1 retry, 120 s timeout; priorities) and the shapes of the ARM bodies and LiteLLM rows they write are deliberate; keep them unless a change asks for it. FastAPI backend + React/Vite frontend; the manager itself can be hosted on App Service with `azd` (either product) or as the public multi-tenant app on Container Apps (`auth_mode=entra`, `deploy/container-apps/`, **APIM only**).

The branch `unified` merged the APIM-only `main` and the LiteLLM-only `liteLLM` branches. The old terminal UI (`tui/`) was dropped.

The older names stay where something depends on them, so don't rename these to SteadyApiPool:
- APIM: the policy markers `<!-- apim-backend-pool:… -->` (`apim/policy.py`, `apim/policy-diff.ts`), `MANAGED_MARKER` "Managed by APIM Backend Pool Manager." (`apim/resources.py`), the `managed-by: apim-backend-pool` tag, the custom role names `APIM Backend Pool Manager` / `APIM Backend Pool Deployment Reader` and their `guid()` seeds in the Bicep, and the default `apimPublisherName` (changing it would update an existing APIM service).
- LiteLLM: `MANAGED_MARKER` "Managed by AI Gateway Pool Manager." (`litellm/resources.py`, how the app recognizes its rows on existing gateways), the `managed-by: ai-gateway-pool` tag, the role names `AI Gateway Pool Manager` / `AI Gateway Pool Deployment Reader` and their seeds.
- Both: the MSAL cache name `apim-backend-pool` in `credentials.py` (remembered sign-ins) and the `ai-gateway-pool:` browser storage keys (`index.html` moves old `apim-backend-pool:` keys over once).

```sh

.venv/Scripts/python -m uvicorn pool_manager.app:app --reload   # :8000
```

CI (`.github/workflows/ci.yml`) runs ruff check, `ruff format --check`, mypy and pytest for the backend (and `mypy --strict` on the packaged scripts), `npm test`, `npm run build`, both Bicep builds and the gateway template check, plus the release package smoke test and the doctor on three OSes. Run the same before you consider a change done.

**Local dev uses your Azure identity (the setup wizard's browser or device-code sign-in, or `az` / `azd` / Azure PowerShell) against a real gateway and real Foundry accounts. Writes are live, and creating a gateway creates billable resources.** Tests don't need Azure.

## Architecture

**Single origin.** FastAPI serves the JSON API under `/api` and the built SPA from `backend/pool_manager/static` (a catch-all route in `app.py`). Same origin is required for the Easy Auth cookie and the CSRF header check. `static/` is build output and is gitignored.

**Products.** `Product = "apim" | "litellm"` (`models.py`, `types.ts`). `Settings.product` follows from the fields: `apim_name` means APIM, `gateway_name`/`gateway_url` LiteLLM (both set is an error). Shared code lives at the top of `pool_manager/` and `frontend/src/`; each product's own code in `apim/` and `litellm/` beside it. Shared code never imports a product package, except the wiring (`deps.py`, `app.py`, `sessions.py` for the public app, `products.ts` on the frontend). When a feature exists for both products, the shared part goes in a base class or shared module and each product supplies hooks; don't copy it into both packages.

**Routes.** Shared routes in `routes.py` under `/api` (config, me, sign-out, setup and its fixes and progress, sign-in, deployments and import, Foundry accounts/models/deploy, target, tenants, subscriptions). Each product's routes in `apim/routes.py` under `/api/apim` and `litellm/routes.py` under `/api/litellm`, guarded by `require_product(product)`, which answers 409 when no gateway or another product's is chosen. The `bound` router (shared) answers 409 until a gateway is chosen. Dependencies come from `deps.py` and `config.get_settings`; `app.py` re-exports them and tests replace them through `app.dependency_overrides` (see `tests/apim/test_app.py::_client`, `tests/litellm/test_app.py::_client`, `tests/apim/test_public.py::_Public`). Locally and with Easy Auth each `get_*` returns a process-wide `lru_cache` singleton; in the public app it returns the caller's session's component. Routes read settings through `get_request_settings`. `GET /api/config` is unauthenticated and tells the browser which mode it is in. A `ServiceError` (`errors.py`) becomes a JSON error with its status code.

**Shared backend** (`backend/pool_manager/`):
- `config.py`: `Settings` (APIM fields `apim_name`, `api_version`, `pool_api_version`, `guest_apim_*`; LiteLLM fields `gateway_*`, `container_apps_api_version`; shared `subscription_id`, `resource_group`, owners, discovery, prefixes, auth), with `product`, `external`, `has_target`, `target_name`. Set in the environment the gateway is fixed: APIM (`POOL_MANAGER_SUBSCRIPTION_ID`, `_RESOURCE_GROUP`, `_APIM_NAME`, all or none), a LiteLLM Container App (`_SUBSCRIPTION_ID`, `_RESOURCE_GROUP`, `_GATEWAY_NAME`), or a LiteLLM gateway elsewhere (`_GATEWAY_NAME` + `_GATEWAY_URL`, with `_GATEWAY_MASTER_KEY`, required when deployed, and optionally `_GATEWAY_PRINCIPAL_ID`, `_GATEWAY_APP_INSIGHTS_ID`). The deployed app requires one. Locally without it, the setup wizard chooses and saves it to `backend/.pool-manager.json` as `{"target": {"product": …, <SAVED_FIELDS[product]>}}` with its tenant (`save_target`, `read_saved_target`; a file from either old branch is read by its fields). `validate_runtime` refuses `auth_mode=entra` unless the target is APIM-only (`_validate_public`).
- `arm.py` (`ArmClient`): a small httpx ARM client. `resource_id` is the gateway's resource (`gateway_resource_id`: the APIM service, the LiteLLM Container App, or `""` for an external gateway), and paths are relative to it; `segment()` escapes path parts, `token_for(scope)` gets other audiences (Log Analytics). Retries/backoff, injectable credential, transport and sleep.
- `target.py` (`TargetChooser`): the setup wizard's gateway step, shared part: tenants, subscriptions, the saved target (`save(product, target)`, `clear`), `require_local`/`require_changeable`. `apim/target.py` (`ApimTargets`) and `litellm/target.py` (`LiteLLMTargets`) wrap it with listing, creating/deploying, connecting and deleting their gateways. After a change `deps.reset_target` rebuilds every gateway-bound factory, keeping the local credential and the secret store.
- `access.py` (`AccessChecker`): the setup wizard. Steps: `sign_in` → `gateway` (`gateway_target`; LiteLLM also `gateway_health`) → `access` (`gateway_access` for the user, `app_gateway` for the app identity, `discovery`, `app_discovery`) → `foundry` (`gateway_identity`, then *Cognitive Services OpenAI User* for the gateway's identity on each member account). It is a template: the base runs the report and the shared checks and fixes; `apim/access.py` (`ApimAccessChecker`, with the `enable_apim_identity` fix) and `litellm/access.py` (`LiteLLMAccessChecker`, `GATEWAY_ACTIONS`) implement the hooks (`gateway_target`, `gateway_access`, `app_gateway`, `gateway_health` when `checks_health`, `gateway_identity`, `gateway_principal`, `user_may_write`, `forget_gateway`) and set `gateway_role`, `gateway_fallback_role`, `discovery_role`, `identity_label`. With no gateway chosen the base alone reports and asks for one. Permissions come from `Microsoft.Authorization/permissions` (wildcards and `notActions`); role definitions are read, not hard-coded. While a report runs it records the step per caller; `GET /api/setup/progress` returns it and `components/startup-progress.tsx` polls it (keep its step kinds in step with `SetupStepKind`). Identities: the *operator* (app MI deployed, the local sign-in locally) does pool work; the *user* (Easy Auth's `X-MS-TOKEN-AAD-*` token deployed, the operator locally, the signed-in user in the public app) runs fixes; the gateway's own MI (APIM's system-assigned one, or the LiteLLM gateway's user-assigned one) calls Foundry.
- `credentials.py` (`LocalCredential`): the local credential: the app's own sign-in (browser, or device code), then Azure CLI, azd and Azure PowerShell, skipping a tool that missed for 60 s; app sign-ins are remembered through MSAL's encrypted cache plus `backend/.pool-manager-auth.json`, never plaintext. Locally, `config.system_trust` makes the lifespan inject `truststore`.
- `discovery.py` (`DeploymentDiscovery`): scans Cognitive Services accounts across the discovery subscriptions (thread pool, 5-minute cache) and imports deployments as members with managed identity auth, through the chosen product's `MemberStore` (`known_members` → `KnownMember`, `add_deployment_member`).
- `model_check.py`: members pointing at a Foundry deployment must serve the same model, read from the deployment's ARM resource. The same read gives each member's deployment type, capacity and per-minute limits (`deployment_quota`: `properties.rateLimits`, else capacity at an older chat model's 1,000 TPM and 6 RPM a unit, none for provisioned throughput), and the check returns the pool's totals, each deployment once. `components/pool-quota.tsx` (pure `pool-quota.ts`) shows them under both products' pool members; on LiteLLM it compares them with `Capabilities.sized_for`, the gateway's `ai-gateway-sizing` tag.
- `model_deploy.py` (`ModelDeployer`): the Deployments tab's **Deploy a model**, all with the **user's** ARM client. Built per request in `routes.py`, so there is no `deps.py` factory to override.
- `metrics.py` (`PoolMonitor`): the Monitor tab's shared part (one-minute cache, `Window`, per-member Azure OpenAI metrics from each Foundry deployment, `ModelDeploymentName`, `interval=FULL`, which include callers outside the pool). Each product's subclass gives the pool and the gateway half (`GatewayReading`). A 403 becomes a message on the tab, never a setup blocker.
- `cost.py` (`CostReader`): the gateway panel's cost: this month's spend, a Cost Management query (`ActualCost`, `MonthToDate`) sent with the **user's** ARM client (`access.user_arm`), cached an hour per caller, and a list price from the public Retail Prices API (no token sent there), cached a day per region. Subclasses give the scope and filter (`spend_scope`, `spend_filter`) and the prices. A missing token, a 403 or an unsupported subscription becomes `month_to_date_note`, never an error.
- `secret_store.py` (`SecretStore`): LiteLLM gateways' master keys in `backend/.pool-manager-gateways.bin`, encrypted with MSAL's persistence (`msal_extensions`); in memory only when the OS has no encryption, never plaintext.
- `models.py`: strict Pydantic models (`extra="forbid"`) shared by the API; each product's own in `apim/models.py` and `litellm/models.py`. `frontend/src/types.ts`, `apim/types.ts` and `litellm/types.ts` mirror them by hand, so keep them in sync.
- `auth.py`: identity comes from the Easy Auth `X-MS-CLIENT-PRINCIPAL-*` headers. Writes need the `X-Pool-Manager: 1` header, which is the CSRF defence, **and** the principal in `POOL_MANAGER_OWNERS` or (with `rbac_writers` and delegated access) the user's own ARM token passing the product's `user_may_write` (APIM: every read/write the app makes; LiteLLM: reading the master key). `owner` (no CSRF header, nothing changes) guards owner-only reads such as LiteLLM's key list. `frontend/src/api.ts` adds that header to every non-GET request. `auth_mode=disabled` is for local dev only and is rejected when `WEBSITE_SITE_NAME` or `CONTAINER_APP_NAME` is set. In the public app (`auth_mode=entra`) the principal is the verified Entra user, `can_write` is always true (Azure decides), and the `X-MS-*` headers are never read.
- `entra.py`, `sessions.py`: the public app (APIM only). `TokenVerifier` checks the browser's bearer token (Entra JWKS via PyJWT, audience `<client id>`/`api://<client id>`, issuer matching the token's own `tid`, the `access_as_user` scope, `entra_allowed_tenants`). `OboExchanger` is an OBO token request whose client assertion comes from the user-assigned managed identity (federated credential; no secret). `UserCredential` holds ARM tokens in memory only and refuses other tenants. `Sessions` builds one `UserSession` (ARM client, `ApimService`, discovery, monitor, tester, cost, access, targets) per verified `(tid/oid, target)` for the service in the `X-Pool-Manager-Target` header (`<sub>/<rg>/<name>`, `parse_target`): every cache lives in one user's session. Sessions end on idle, LRU when full (at most 8 per user), or `POST /api/session/sign-out`; it rate-limits per user. The guest view (`guest_*` settings, `X-Pool-Manager-Guest: 1`, `deps.get_guest`) is one shared read-only session with the app's managed identity (built-in Reader, `deploy/container-apps/infra/modules/guest-reader.bicep`); `acting_user`, `writer`, `AccessChecker.require_user` and the target chooser refuse it.

**APIM** (`backend/pool_manager/apim/`):
- `service.py` (`ApimService`): all APIM operations and the safety rules; translates `ArmError` into `ServiceError`.
- `resources.py`: ARM request bodies (Single/Pool backends, circuit breakers) and readbacks into views.
- `policy.py`: edits API policy XML via marker comments (`<!-- apim-backend-pool:inbound:begin -->` …). It only rewrites its own blocks. The original `<backend>` section is base64-encoded into the marker so unbinding restores the policy **byte for byte**. It raises `PolicyConflict` when a policy's backend section isn't simple enough to take over.
- `target.py` (`ApimTargets`): lists, creates, soft-deletes and restores APIM services.
- `api_test.py` (`ApimTester`): keys (APIM subscriptions) are listed, created and read with the **user's** ARM client (`AccessChecker.require_user`), never the app identity. The test call goes from the backend to this service's gateway because the gateway sends no CORS headers.
- `metrics.py` (`ApimMonitor`): APIM metrics have no backend dimension, so pool numbers come from the bound APIs (`ApiId`). `cost.py` (`ApimCost`): spend on the service's resource group filtered to its resource ID; list price from the `<tier> Unit` hourly price × units × 730 plus the `<tier> Calls` overage (`RETAIL_TIERS`).

**LiteLLM** (`backend/pool_manager/litellm/`):
- Concepts. A *gateway* is a LiteLLM proxy with a database (`STORE_MODEL_IN_DB`). A *pool* is a LiteLLM model group: one row in the model table per member, `model_name = <pool id>`, `litellm_params.model = azure/<deployment>`, `api_base`, `order = priority + 1`, `weight`, `num_retries`, `timeout`, and `model_info.id = <pool>--<member>`, `allowed_fails`, `cooldown_time`. `model_info.pool_manager` holds what LiteLLM has no field for (`managed_by: MANAGED_MARKER`, the pool's title/description/aliases, the member's id/title/url/auth/position). Clients call `<gateway>/v1` with the pool ID as the model, or an alias (`router_settings.model_group_alias`). Members authenticate with the gateway's managed identity (`enable_azure_ad_token_refresh`, `AZURE_CLIENT_ID`), or with an API key kept in a LiteLLM credential (`litellm_credential_name`). Session pinning for the Responses API is gateway-wide (`optional_pre_call_checks` in the config), not a pool setting.
- `gateway.py` (`GatewayConnection`): finds the gateway and its admin client. For a Container App it reads, through ARM, the ingress FQDN, the user-assigned identity, the App Insights component (tag `ai-gateway-app-insights`) and the master key (`POST listSecrets`, secret `litellm-master-key`), cached 60 s and held in the server process only, never sent to the browser. An external gateway's key comes from the settings or the `SecretStore`.
- `client.py` (`LiteLLMClient`): a small httpx client for LiteLLM's admin API with the master key (`/model/info|new|delete`, `PATCH /model/{id}/update`, `/router/settings`, `/config/update`, `/key/list|generate|delete`, `/credentials`, `/health/readiness`), retries on 429/5xx, `LiteLLMError`. Injectable transport and sleep.
- `service.py` (`LiteLLMService`): all pool, member, alias, config and removal operations and the safety rules; translates `LiteLLMError` / `GatewayUnavailable` into `ServiceError`.
- `resources.py`: builds rows (`pool_row`, `member_params`), parses them back into views (`parse_pool`, `row_member`), the pool ETag (`pool_etag`, a hash of the rows without aliases and timestamps) and the YAML config view (`config_yaml`).
- `target.py` (`LiteLLMTargets`): gateways (Container Apps tagged `managed-by: ai-gateway-pool` or running LiteLLM's image), deploy (`gateway_deploy.py`), its status, connect/disconnect an external gateway, and delete.
- `capacity.py` (`CapacityCheck`): read-only, before anything is created: the region offers each resource type the template creates (provider `resourceTypes[].locations`), everything from the sizing plan: PostgreSQL (capabilities: restriction, version 16, the plan's SKU in its edition, `sizing.POSTGRES_SIZES`; `resourceType/flexibleServers/usages`: that SKU's family, `standardBSFamily` or `standardDDSv5Family`, which some regions don't list, and `cores`), Redis only when the plan has it, Container Apps (`Microsoft.App/locations/{loc}/usages`: `ManagedEnvironmentCount`), AKS (the plan's node SKU, its zones, `standardDDSv5Family`/`cores` for its most nodes). Every problem at once; `open_regions` runs the same checks on a few common regions. A check that can't be read is skipped. `POST /litellm/target/gateways/preflight` returns it for the deploy form, with the plan and its retail price in the region (`cost.PlanPrices`).
- `cleanup.py`: `DELETE_ORDER`, `tagged_resources` and `delete_resources`, shared by deleting a gateway and by `GatewayCleanup`, the background cleanup after a failed deployment (process-wide, `deps._cleanups`, not reset on a gateway switch; one job per deployment and start time; passes every 30 s until two in a row find nothing to ask, retrying refused deletes, up to 45 minutes).
- `sizing.py` (`plan`, `plans`): the capacity sizer, pure arithmetic from a `GatewaySizing` (peak RPM, average input and output tokens, timeout, streaming, model speed or response time, headroom, zone redundancy, AKS team, GPU models, private network) to a `GatewayPlan` per platform: requests a second, tokens a minute, call time, calls in flight (and slowed to the timeout), gateway CPU per call and per replica, replicas (peak, headroom, one spare for a zone, at least two), Postgres size by connections (Burstable only for one replica), Redis by peak, AKS nodes and outbound ports, and notes (`PlanNoteCode`: reasons, warnings, problems, worded by the UI's `planNote_*` keys and in English by `describe` for refusals). It recommends AKS when Container Apps can't take it: a call that may be silent past 240 s (measured; streaming keeps a request open), more than `ACA_MAX_REPLICAS`, an AKS team or GPU models. The CPU constants were measured with `calibrate.py` (dated in `sizing.py`; streaming dominates: about 0.75 ms a chunk, plus OpenTelemetry's 0.11 ms a chunk per 1,000 prompt tokens); re-run it when LiteLLM's version changes. The memory ones are estimates. `POST /litellm/target/gateways/plan` returns both platforms' plans and reads nothing.
- `resize.py` (`GatewayResizer`): resizing a gateway this app deployed for a new scenario, with the user's own ARM token (`require_user`). `POST /litellm/gateway/resize/plan` reads the gateway and lists the changes (`ResizeChange`: `apply`, `optional` for the database, `manual` with a command for what it doesn't change in place: node size, AKS outbound ports and tier, Redis, timeouts) and an `etag` of what it read; `POST /litellm/gateway/resize` recomputes, refuses a changed gateway, and applies: on Container Apps a PATCH of the template (scale range, HTTP rule, LiteLLM's resources) and tags; on AKS a PUT of the agent pool, the cluster's tags (`ai-gateway-install`) and Run Command `helm upgrade --reuse-values` with the pod range (followed by `GET .../resize/{command}`); the Postgres SKU (PATCH) only when asked. The UI (`resize-dialog.tsx`, from the gateway panel) warns that production traffic may be affected and needs a confirmation.
- `gateway_deploy.py` (`GatewayDeployer`) + `gateway_template.py`: one ARM deployment `ai-gateway-<name>` of the compiled template, with parameters the backend generates (`aca_parameters`: new master key, salt key and Postgres password; `litellm_config`, `collector_config`). The sizes are the sizing plan's (`sizing.py`), passed as template parameters (replicas and their size, the scale rule, the Postgres SKU and tier, the Redis SKU or none; on AKS the node size and range, tier, outbound IPs and ports) and kept as tags on the Container App or cluster (`ai-gateway-postgres`, `ai-gateway-redis`, `ai-gateway-sizing` = `sizing_tag`, on AKS `ai-gateway-install` = `InstallSize`, which the install reads); `ai-gateway-profile` stays as a label (dev = one replica). The Container Apps environment is a workload profiles one (LiteLLM on its Consumption profile), whose ingress ends a request that sends nothing for 240 s. LiteLLM's config takes the plan's timeout and database pool and batches spend writes (`proxy_batch_write_at: 60`). On AKS each pod is 1 vCPU / 4 GiB (`AKS_POD_RESOURCES`, requests and limits) and the route timeout covers a call and its retry. `LITELLM_VERSION` pins the image in one place; the AKS bundle (`aks_bundle`: Helm `values.yaml` for `oci://ghcr.io/berriai/litellm-helm`, `deploy.sh` with workload identity and Postgres, README) pins the same.
- `aks_deploy.py` (`AksDeployer`): a gateway on a new AKS cluster, in three phases followed by `status` (`GatewayDeployStatus.phase`): the ARM deployment of `templates/litellm-aks.json` (tagged `ai-gateway-platform: aks`); then AKS Run Command (`runCommand` with the user's `clusterToken` for the AKS server app `6dae42f8-…`, then `commandResults/{id}`) running `gateway_template.aks_bootstrap` (cert-manager, the collector, LiteLLM's chart, the `approuting-istio` Gateway with a Let's Encrypt certificate on `<name>.<region>.cloudapp.azure.com`); then waiting for LiteLLM to answer there over trusted HTTPS. The deploy saves the target as an external gateway with `gateway_cluster_id` and `gateway_provisioning: aks` (setup reports `DeployingAks`; the picker's progress, which polls the status, drives the install on), and finishing replaces it with the identity and App Insights IDs. Preflight (read-only): DNS label free, node SKU and its zones, vCPU quota, `roleAssignments/write`, PostgreSQL in the region. `retry_install` runs the install again after a failure.
- `api_test.py` (`LiteLLMTester`): keys are LiteLLM virtual keys, listed and made with the master key (owners only). The test call goes from the backend to the gateway's `/v1`. `target(pool_id, model)` holds the rules (the gateway's URL, HTTPS unless local, only the pool's model names) shared with the load test.
- `benchmark.py`: the load test. `run_benchmark` is a closed loop (async httpx: each simulated user sends a request, waits, sends the next, until the duration or `max_requests`; ramp-up and a rate cap; streaming with `stream_options.include_usage` measures time to first token) that records a `Sample` per request, including the member (`x-litellm-model-id`) and failovers (`x-litellm-attempted-fallbacks`). `summarize` (pure) gives nearest-rank percentiles, errors with 429s apart, per-member shares and a per-second timeline. `BenchmarkRunner` (`deps.get_benchmarks`) runs one test at a time on its own thread and keeps the last five in memory. Routes `POST /litellm/pools/{id}/benchmarks` (`Writer`), `GET .../{run}` (`Owner`), `POST .../{run}/stop`; the key in `BenchmarkStart` is a `SecretStr`, only sent to the gateway, never returned, logged or stored. Limits (`BENCHMARK_MAX_*` in `litellm/models.py`: 50 users, 600 s, 5,000 requests) are mirrored in `frontend/src/litellm/benchmark.ts`. `scripts/benchmark.py` is the same engine from a terminal (`--i-know` lifts the limits there only; `main(argv, transport=...)` for tests in `tests/litellm/test_benchmark_cli.py`).
- `metrics.py` (`LiteLLMMonitor`): gateway numbers come from the gateway's OpenTelemetry spans (one `chat <pool>` span per attempt, with `server.address`, `litellm.provider.model`, `error.type`, tokens) in its Application Insights component, queried through the Log Analytics resource-context API (`https://api.loganalytics.azure.com/v1<component id>/query`, token for `api.loganalytics.io`). Requests are grouped by `operation_Id`, so retries and failovers show. Without a component the gateway half is `no_app_insights`. `/spend/logs` is not used: it stops writing success rows. `cost.py` (`LiteLLMCost`): spend filtered by tag `ai-gateway: <name>`; list price a monthly low–high range (Container Apps vCPU/memory idle to active, or AKS nodes and tier, PostgreSQL Flexible compute and storage, Redis) at the sizes the gateway's tags say (a gateway from before them by its profile); `PlanPrices` prices a plan before it exists.

**Invariants to preserve when changing service logic.** Both products:
- Rows, backends and APIs this app didn't write (no `MANAGED_MARKER`) are shown read-only and never changed or deleted. IDs starting with a protected prefix (`POOL_MANAGER_PROTECTED_PREFIXES`) are read-only too.
- Every pool save runs `model_check.py`; members whose model can't be read fail. `POST /api/{product}/pools/model-check` is the read-only version the editor uses.
- Members are managed inside their pool; there is no backends page. Imports always land in a pool. When a save drops members, or a pool goes, the members this app created that no pool uses any more go with it (APIM `_delete_orphans`, with their credential named value; LiteLLM rows plus `_delete_unused_credentials`); cleanup failures are logged, not raised.
- The breaker/cooldown is a pool setting (`PoolWrite.circuit_breaker`) written to every member this app manages; LiteLLM also writes `retries` and `timeout_seconds` to every row. `frontend/src/{apim,litellm}/pool-breaker.ts` hold the defaults the UI starts from.
- Removing a pool, and the gateway-wide cleanup, go through a read-only plan (`GET /pools/{id}/removal`, `GET /cleanup`) and then `POST` the plan the user reviewed (`RemovalConfirm`; cleanup also needs the gateway name typed again). `_remove` recomputes the plan and refuses anything the user didn't see. Cleanup takes only pools this app created and leaves the gateway itself.
- Deploying a model runs with the user's own ARM token (`require_user`), never the app identity. Only accounts the discovery scan finds take a deployment; the model, version, deployment type and capacity are checked against that account's `models` list, and an existing deployment name is never replaced. Only OpenAI-format models and the pay-per-token types (GlobalStandard, DataZoneStandard, Standard) are offered; fine-tune SKUs are skipped.
- Setup fixes run with the **user's** token, never the app identity, and the app identity never gets `roleAssignments/write`. Grants are limited to *Cognitive Services OpenAI User* for the gateway's managed identity on accounts that are pool members or discovered (`grant_foundry_access` refuses others), with deterministic assignment names so retries are idempotent. Fix endpoints need the CSRF header and sign-in but not the owners list, because Azure itself authorizes them.
- Creating or deleting a gateway is local setup only, uses the signed-in user's own rights, is limited to gateways carrying the product's `managed-by` tag, needs the name typed again (checked by the backend, not just the UI), and never deletes a resource group. Deleting the current gateway clears `backend/.pool-manager.json`.

APIM:
- Every update is ETag-conditional (`If-Match`, or `If-None-Match: *` on create).
- Creating a service checks the name first, creates with `If-None-Match: *` and tags it `managed-by: apim-backend-pool`. It may register `Microsoft.ApiManagement` and create a missing resource group, but never changes an existing service or resource group. Consumption is not offered (no circuit breaker). Deleting soft-deletes: Azure keeps the service 48 hours and `restore` (PUT with `properties.restore: true`) brings it back; the app never purges.
- Members still in a pool can't be deleted, and `DELETE /pools/{id}` refuses a pool still bound to an API. `_remove` unbinds other APIs first (restoring their policy), then deletes the APIs this app created for the pools, the pools, and the orphaned members.
- APIs created for pools (`create_pool_api`) carry `MANAGED_MARKER`. The app only creates APIs (`If-None-Match: *`) or finishes one it created earlier for the same pool and path. It deletes an API only when it carries the marker (checked again right before the ETag-conditional DELETE) and its pool is being removed; `api_pool_id` reads which pool it was created for.
- Subscription keys are read only for subscriptions whose scope opens the API being tested, never the built-in `master` one, and never logged or stored. The only subscription the app writes is one test subscription per API (`<id_prefix>test-<api>`, scoped to that API). The test call only POSTs below the path of an API bound to a pool, on this service's HTTPS gateway, and returns a filtered set of response headers (no cookies).
- Pool reads and writes use `pool_api_version` (preview by default) because GA `2024-05-01` drops `pool.sessionAffinity`. Everything else uses `api_version` (GA).
- The public app stores nothing server-side: no tokens beyond the in-memory session, no state file (`TargetChooser` never saves there; the browser keeps the choice), no secret. Sessions are keyed by the verified tenant and object ID only. Its settings refuse a fixed service or `discovery_subscriptions`. Its test call only goes to Azure's gateway host names (`AZURE_GATEWAY_SUFFIXES`, no explicit port). It sends a Content-Security-Policy (inline scripts by hash, Entra only for connect/frame/form), and only `/redirect.html` may be framed, for MSAL's silent renewal.

LiteLLM:
- A deployment's sizes are the plan the backend computes from the scenario in the request (`GatewayDeployer.plan`), never sizes from the browser; a plan with problems is refused before anything is read or created.
- Nothing is created before the region passes `require_capacity` and ARM's `validate` of the exact deployment body (`deploy`); when validation fails, an empty resource group created for it is deleted again. A deployment with `cleanup_on_failure` (the default) carries the tag `ai-gateway-on-failure: delete`; `LiteLLMTargets.deploy_status` (`_follow_failure`) then cancels it (`POST .../cancel`) as soon as a step failed, and once it has stopped starts `GatewayCleanup`, which deletes only the resources tagged `managed-by` and `ai-gateway: <name>` (never the resource group), keeps the deployment record for its error, and forgets an AKS install's pending keys. Only the Azure phase: a failed AKS install is retried, not deleted.
- Deploying a gateway refuses a name whose Container App exists or whose deployment is running or done, registers the providers the template needs, creates a missing resource group (tagged `managed-by`) and never changes an existing resource group or gateway. The only change to an existing gateway is a resize the user reviewed and confirmed (`resize.py`), on a gateway tagged as this app's, with the user's own rights, against an `etag` of the gateway as the plan read it. Every resource carries `managed-by: ai-gateway-pool` and `ai-gateway: <name>`. The secrets are generated once, by the backend, for that deployment: a gateway is never redeployed, because a new salt key would make stored member keys unreadable. Deleting takes only the resources tagged `ai-gateway: <name>` (Container App first, then its environment, then the rest). There is no soft-delete: its database (pools, keys, spend) is gone, and the dialog says so.
- Deploying on AKS also grants the user *Azure Kubernetes Service RBAC Cluster Admin* on the new cluster (Entra ID with Azure RBAC, no local accounts). The secrets are made once, kept in `SecretStore` under `aks-install:<cluster id>` before the deployment is PUT, and reach the cluster only as files in Run Command's context; the install script creates Kubernetes secrets only when missing, so re-running it never rotates them, and it never prints them. Once LiteLLM answers, only the master key stays, under the gateway's URL. From then on the cluster is the user's: the app doesn't upgrade it and only manages pools in LiteLLM, except a resize the user asks for in the gateway panel (the node pool's range and LiteLLM's pods, after the warning and confirmation), and shows maintenance commands (`frontend/src/litellm/aks-maintenance.ts`). Deleting it is as for Container Apps, with the cluster in `_DELETE_ORDER` beside the environment (not waited for) and its stored keys forgotten.
- Connecting an external gateway checks readiness, the database and the master key against the gateway before saving; the key goes to `SecretStore`, never the state file. Disconnecting forgets the key and doesn't touch the gateway.
- LiteLLM has no ETags. `PoolView.etag` is the hash of the pool's rows, and a save re-reads and compares it (409 on mismatch); a create sends no ETag and fails if the pool or an alias of that name exists. Writes go create → update → delete, so a pool never runs empty mid-save. This is best-effort, not atomic; a failure reports what was already done.
- Aliases are `router_settings.model_group_alias` entries, replaced as a whole through `/config/update`. An alias may not shadow a pool ID or another alias. The aliases this app added are recorded in the pool's rows (`pool_manager.pool.aliases`) and excluded from the ETag. Removal deletes this app's aliases first and unbinds others pointing at the pool, then the pool's test keys, then the rows.
- Virtual keys: LiteLLM keeps only a hash, so a key is shown once, when created, and never stored or logged by this app. The only key this app writes is one test key per pool (alias `<id_prefix>test-<pool>`, `metadata.pool_manager.pool`, `models` = the pool's names); creating it again deletes the old one first (`/key/regenerate` is Enterprise-only). The test call only goes to the gateway's own `/v1` (HTTPS unless running locally), only with a model name of the pool, and returns a filtered set of response headers (no cookies, no cost headers); `x-litellm-model-id` says which member answered.
