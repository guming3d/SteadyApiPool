# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**SteadyApiPool** (repository `guming3d/SteadyApiPool`, formerly `apim-backend-pool-manager`): a manager for a **LiteLLM AI gateway** in front of Azure OpenAI / Foundry deployments, for people who know neither LiteLLM nor Foundry. It deploys the gateway (Azure Container Apps in one step, or a new AKS cluster it installs LiteLLM on and then hands over, or the files for an existing cluster), discovers Foundry deployments, groups deployments of one model into **pools** (LiteLLM model groups) with failover, weights and cooldown, exposes them under model names and aliases, and gives a call guide with a virtual key, a test call and a Monitor tab. Its defaults (cooldown on the first failure for 60 s, 1 retry, 120 s timeout, priorities) and the shapes of the rows it writes are deliberate; keep them unless a change asks for it. FastAPI backend + React/Vite frontend; the manager itself can be hosted on App Service with `azd`.

The repository started as an Azure API Management (APIM) backend-pool manager; the `main` branch still is one. On this branch the **terminal UI (`tui/`) and the public multi-tenant app (`auth_mode=entra`, `deploy/container-apps/`) still target APIM** and are frozen: `start-local --tui` refuses, the backend refuses to start with `auth_mode=entra`, and neither is in CI or the release package.

The older names stay where something depends on them, so don't rename these to SteadyApiPool: `MANAGED_MARKER` ("Managed by AI Gateway Pool Manager.", how the app recognizes its rows on existing gateways), the custom role names `AI Gateway Pool Manager` / `AI Gateway Pool Deployment Reader` (looked up by `access.py`), the `managed-by: ai-gateway-pool` tag, the `ai-gateway-pool:` storage keys, and the MSAL cache name `apim-backend-pool` in `credentials.py` (remembered sign-ins).

## Commands

Backend (run from `backend/`; on Windows the venv uses `.venv/Scripts/`, on POSIX `.venv/bin/`):

```sh
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt pytest==9.1.1 ruff==0.15.22 mypy==2.3.0
cp .env.example .env                                   # POOL_MANAGER_* settings; the gateway is chosen in the app
.venv/Scripts/python -m uvicorn pool_manager.app:app --reload   # :8000
.venv/Scripts/python -m pytest -q
.venv/Scripts/python -m pytest -q tests/test_pools.py::<test_name>  # single test
.venv/Scripts/python -m pytest -q -m litellm           # opt-in: a real LiteLLM in Docker (tests/litellm_stack)
.venv/Scripts/python -m ruff check . ../scripts && .venv/Scripts/python -m ruff format --check . ../scripts
.venv/Scripts/python -m mypy                           # strict, configured in pyproject.toml
```

`pytest -m litellm` needs `docker compose -f tests/litellm_stack/docker-compose.yml up -d` first: Postgres, LiteLLM (pinned to the same version as the template) on :14000 and two fake Azure OpenAI upstreams (`fake_upstream.py`, `/control` makes one fail). It checks failover by `order`, cooldown, aliases, key scoping and `x-litellm-model-id` against the real proxy.

Both servers at once, with prerequisite/`.env` checks and installs only when needed: `scripts/start-local.ps1` (Windows; `start-local.cmd` bypasses the execution policy) or `scripts/start-local.sh`. They first run `scripts/doctor.py --brief` (`-SkipChecks` / `--skip-checks` to skip). Without Node.js 22+ (or with `-Prebuilt` / `--prebuilt`) they skip Vite and the backend serves the built UI on :8000.

Frontend (run from `frontend/`):

```sh
npm ci
npm run dev        # :5174, proxies /api to :8000 (override with API_PROXY_TARGET)
npm test           # node --test tests/*.test.mjs (imports src/*.ts directly)
node --test --test-name-pattern "<name>" tests/pool-modes.test.mjs   # single test
npm run typecheck
npm run build      # outputs to ../backend/pool_manager/static
```

`backend/.venv/Scripts/python scripts/benchmark.py --url https://<gateway>/v1 --model <pool>` load-tests a pool from a terminal (key in `LITELLM_KEY`; `--preset smoke|typical|stress`, `--help` for the rest). Every request is billed like real traffic.

`backend/.venv/Scripts/python scripts/demo_server.py` serves the built UI on :8010 against `tests/fake_azure.py` and `tests/fake_litellm.py` (no Azure; the real credential factories and the secret store refuse to build). `POST /demo/stage/{sign-in,ready,pool}` resets it to a point in onboarding; a gateway deployed from its wizard finishes after a few status polls. The README's Get started screenshots in `docs/images/` come from it; retake them when the UI they show changes.

The gateway templates: `infra/gateway/litellm-aca.bicep` and `litellm-aks.bicep` are compiled into `backend/pool_manager/templates/litellm-{aca,aks}.json`, which the app deploys. After changing either Bicep run `python scripts/build-gateway-template.py`; CI runs it with `--check` (generator metadata ignored). Both stay flat (no modules), so the deployment's operations name the real resources the progress shows.

Environment preflight and release: `python scripts/doctor.py` (stdlib only, Python 3.8 syntax so it can say "too old" on old Pythons; per-OS install commands, Node/prebuilt decision, sign-in tools, headless/SSH/WSL, keyring, DNS/TLS/proxy to Entra, ARM and the package indexes; tests in `backend/tests/test_doctor.py`). `python scripts/package-release.py` zips backend (with `static/` and `templates/`), the scripts and README into `dist/`, which needs Python only; `.github/workflows/release.yml` publishes it on `v*` tags. `.gitattributes` pins `*.sh` to LF so WSL can run a Windows checkout.

Infra (hosting the manager): `az bicep build --file infra/main.bicep --stdout > /dev/null`. Deploy: `azd provision --preview`, then `azd up`, after deploying the gateway (it isn't created by this Bicep). The `prepackage` hook in `azure.yaml` builds the frontend into the backend package.

CI (`.github/workflows/ci.yml`) runs ruff check, `ruff format --check`, mypy and pytest for the backend (and `mypy --strict` on the packaged scripts), `npm test`, `npm run build`, the Bicep build and the gateway template check. Run the same before you consider a change done.

**Local dev uses your Azure identity (the setup wizard's browser or device-code sign-in, or `az` / `azd` / Azure PowerShell) against a real gateway and real Foundry accounts. Writes are live, and deploying a gateway creates billable resources.** Tests don't need Azure.

## Architecture

**Single origin.** FastAPI serves the JSON API under `/api` and the built SPA from `backend/pool_manager/static` (a catch-all route in `app.py`). Same origin is required for the Easy Auth cookie and the CSRF header check. `static/` is build output and is gitignored.

**Concepts.** A *gateway* is a LiteLLM proxy with a database (`STORE_MODEL_IN_DB`). A *pool* is a LiteLLM model group: one row in the model table per member, `model_name = <pool id>`, `litellm_params.model = azure/<deployment>`, `api_base`, `order = priority + 1`, `weight`, `num_retries`, `timeout`, and `model_info.id = <pool>--<member>`, `allowed_fails`, `cooldown_time`. `model_info.pool_manager` holds what LiteLLM has no field for (`managed_by: MANAGED_MARKER`, the pool's title/description/aliases, the member's id/title/url/auth/position). Clients call `<gateway>/v1` with the pool ID as the model, or an alias (`router_settings.model_group_alias`). Members authenticate with the gateway's managed identity (`enable_azure_ad_token_refresh`, `AZURE_CLIENT_ID`), or with an API key kept in a LiteLLM credential (`litellm_credential_name`). Session pinning for the Responses API is gateway-wide (`optional_pre_call_checks` in the config), not a pool setting.

**Backend layering** (`backend/pool_manager/`):
- `app.py`: routes only. Routes that work on the gateway sit on the `bound` router, which answers 409 until a gateway is chosen. Dependencies come from `deps.py` (`get_arm`, `get_service`, `get_discovery`, `get_access`, `get_targets`, `get_tester`, `get_monitor`, `get_cost`) and `config.get_settings`; `app.py` re-exports them and tests replace them through `app.dependency_overrides` (see `tests/test_app.py::_client`). Each `get_*` returns a process-wide `lru_cache` singleton (`_arm`, `_gateway`, `_secrets`, `_service`, ...). Routes read settings through `get_request_settings`. `GET /api/config` is unauthenticated and tells the browser which mode it is in. A `ServiceError` becomes a JSON error with its status code.
- `config.py`: the gateway. Set in the environment it is fixed: a Container App (`POOL_MANAGER_SUBSCRIPTION_ID`, `_RESOURCE_GROUP`, `_GATEWAY_NAME`, all or none), or a gateway elsewhere (`_GATEWAY_NAME` + `_GATEWAY_URL`, with `_GATEWAY_MASTER_KEY`, required when deployed, and optionally `_GATEWAY_PRINCIPAL_ID`, `_GATEWAY_APP_INSIGHTS_ID`). The deployed app requires one. Locally without it, the setup wizard chooses and saves it to `backend/.pool-manager.json` (with its tenant; an APIM-era file is ignored). `validate_runtime` refuses `auth_mode=entra`.
- `gateway.py` (`GatewayConnection`): finds the gateway and its admin client. For a Container App it reads, through ARM, the ingress FQDN, the user-assigned identity, the App Insights component (tag `ai-gateway-app-insights`) and the master key (`POST listSecrets`, secret `litellm-master-key`), cached 60 s and held in the server process only, never sent to the browser. An external gateway's key comes from the settings or the local `SecretStore`.
- `litellm.py` (`LiteLLMClient`): a small httpx client for LiteLLM's admin API with the master key (`/model/info|new|delete`, `PATCH /model/{id}/update`, `/router/settings`, `/config/update`, `/key/list|generate|delete`, `/credentials`, `/health/readiness`), retries on 429/5xx, `LiteLLMError`. Injectable transport and sleep.
- `service.py` (`PoolManagerService`): all pool, member, alias, config and removal operations and the safety rules; translates `LiteLLMError` / `GatewayUnavailable` into `ServiceError`.
- `resources.py`: builds rows (`pool_row`, `member_params`), parses them back into views (`parse_pool`, `row_member`), the pool ETag (`pool_etag`, a hash of the rows without aliases and timestamps) and the YAML config view (`config_yaml`).
- `arm.py` (`ArmClient`): a small httpx ARM client. `resource_id` is the gateway's Container App (`""` for an external gateway), `segment()` escapes path parts, `token_for(scope)` gets other audiences (Log Analytics). It handles retries/backoff and takes an injectable credential, transport and sleep.
- `target.py` (`TargetChooser`): the setup wizard's gateway step: tenants, subscriptions, gateways (Container Apps tagged `managed-by: ai-gateway-pool` or running LiteLLM's image), deploy (`gateway_deploy.py`), its status, connect/disconnect an external gateway, and delete. After a change `deps.reset_target` rebuilds every gateway-bound factory, keeping the local credential and the secret store.
- `aks_deploy.py` (`AksDeployer`): a gateway on a new AKS cluster, in three phases followed by `status` (`GatewayDeployStatus.phase`): the ARM deployment of `templates/litellm-aks.json` (tagged `ai-gateway-platform: aks`); then AKS Run Command (`runCommand` with the user's `clusterToken` for the AKS server app `6dae42f8-…`, then `commandResults/{id}`) running `gateway_template.aks_bootstrap` (cert-manager, the collector, LiteLLM's chart, the `approuting-istio` Gateway with a Let's Encrypt certificate on `<name>.<region>.cloudapp.azure.com`); then waiting for LiteLLM to answer there over trusted HTTPS. The deploy saves the target as an external gateway with `gateway_cluster_id` and `gateway_provisioning: aks` (setup reports `DeployingAks`; the picker's progress, which polls the status, drives the install on), and finishing replaces it with the identity and App Insights IDs. Preflight (read-only): DNS label free, node SKU and its zones, vCPU quota, `roleAssignments/write`, PostgreSQL in the region. `retry_install` runs the install again after a failure.
- `gateway_deploy.py` (`GatewayDeployer`) + `gateway_template.py`: one ARM deployment `ai-gateway-<name>` of the compiled template, with parameters the backend generates (`aca_parameters`: new master key, salt key and Postgres password; `litellm_config`, `collector_config`). Profiles: dev (1 replica, B1ms, no Redis), production (2–5 replicas, B2s, Azure Managed Redis). `LITELLM_VERSION` pins the image in one place; the AKS bundle (`aks_bundle`: Helm `values.yaml` for `oci://ghcr.io/berriai/litellm-helm`, `deploy.sh` with workload identity and Postgres, README) pins the same.
- `secret_store.py` (`SecretStore`): external gateways' master keys in `backend/.pool-manager-gateways.bin`, encrypted with MSAL's persistence (`msal_extensions`); in memory only when the OS has no encryption, never plaintext.
- `api_test.py` (`ApiTester`): the call guide's key step and test call. Keys are LiteLLM virtual keys, listed and made with the master key (owners only). The test call goes from the backend to the gateway's `/v1` because the gateway sends no CORS headers for this origin. `target(pool_id, model)` holds the rules (the gateway's URL, HTTPS unless local, only the pool's model names) shared with the load test.
- `benchmark.py`: the load test. `run_benchmark` is a closed loop (async httpx: each simulated user sends a request, waits, sends the next, until the duration or `max_requests`; ramp-up and a rate cap; streaming with `stream_options.include_usage` measures time to first token) that records a `Sample` per request, including the member (`x-litellm-model-id`) and failovers (`x-litellm-attempted-fallbacks`). `summarize` (pure) gives nearest-rank percentiles, errors with 429s apart, per-member shares and a per-second timeline counted by completion time. `BenchmarkRunner` (`deps.get_benchmarks`, in the public app one per session) runs one test at a time on its own thread and keeps the last five in memory. Routes `POST /pools/{id}/benchmarks` (`Writer`), `GET .../{run}` (`Owner`), `POST .../{run}/stop`; the key in `BenchmarkStart` is a `SecretStr`, only sent to the gateway, never returned, logged or stored. Limits (`BENCHMARK_MAX_*` in `models.py`: 50 users, 600 s, 5,000 requests) are mirrored in `frontend/src/benchmark.ts`. `scripts/benchmark.py` is the same engine from a terminal (`LITELLM_KEY`, presets, `--json`/`--csv`, Ctrl+C still reports, `--i-know` lifts the limits there only; `main(argv, transport=...)` for tests in `tests/test_benchmark_cli.py`).
- `metrics.py` (`PoolMonitor`): the Monitor tab, read-only, one-minute cache. Gateway numbers come from the gateway's OpenTelemetry spans (one `chat <pool>` span per attempt, with `server.address`, `litellm.provider.model`, `error.type`, tokens) in its Application Insights component, queried through the Log Analytics resource-context API (`https://api.loganalytics.azure.com/v1<component id>/query`, token for `api.loganalytics.io`). Requests are grouped by `operation_Id`, so retries and failovers show. Without a component the gateway half is `no_app_insights`. Per-member numbers come from each Foundry deployment's Azure OpenAI metrics (`ModelDeploymentName`, `interval=FULL`) and include callers outside the pool. A 403 becomes a message on the tab, never a setup blocker. `/spend/logs` is not used: it stops writing success rows.
- `cost.py` (`CostReader`): the gateway panel's cost. This month's spend is a Cost Management query (`ActualCost`, `MonthToDate`) filtered by tag `ai-gateway: <name>`, sent with the **user's** ARM client (`access.user_arm`), cached an hour per caller. The list price is a monthly low–high range from the public Retail Prices API (no token sent there): Container Apps vCPU/memory (idle to active), PostgreSQL Flexible compute and storage, Redis for production, cached a day per region. A missing token, a 403, an external gateway or an unsupported subscription becomes `month_to_date_note`, never an error.
- `discovery.py`: scans Cognitive Services accounts across the discovery subscriptions (thread pool, 5-minute cache) and imports deployments as members with managed identity auth.
- `model_check.py`: members pointing at a Foundry deployment must serve the same model, read from the deployment's ARM resource.
- `model_deploy.py` (`ModelDeployer`): the Deployments tab's **Deploy a model**, all with the **user's** ARM client. Built per request in `app.py`, so there is no `deps.py` factory to override.
- `models.py`: strict Pydantic models (`extra="forbid"`) shared by the API. `frontend/src/types.ts` mirrors them by hand, so keep the two in sync.
- `auth.py`: identity comes from the Easy Auth `X-MS-CLIENT-PRINCIPAL-*` headers. Writes need the `X-Pool-Manager: 1` header, which is the CSRF defence, **and** the principal in `POOL_MANAGER_OWNERS`; `owner` (no CSRF header, nothing changes) guards owner-only reads such as the key list. `frontend/src/api.ts` adds that header to every non-GET request. `auth_mode=disabled` is for local dev only and is rejected when `WEBSITE_SITE_NAME` or `CONTAINER_APP_NAME` is set.
- `access.py` (`AccessChecker`): the setup wizard. Steps: `sign_in` → `gateway` (`gateway_target`, with the deployment's progress while it runs; `gateway_health`: readiness, database, master key) → `access` (`gateway_access` for the user, `app_gateway` for the app identity: `containerApps/read` + `listSecrets/action`, `GATEWAY_ACTIONS`; `discovery`, `app_discovery`) → `foundry` (`gateway_identity`, then *Cognitive Services OpenAI User* for the gateway's identity on each member account). Permissions come from `Microsoft.Authorization/permissions` (wildcards and `notActions`); role definitions are read, not hard-coded. While a report runs it records the step per caller; `GET /api/setup/progress` returns it and `components/startup-progress.tsx` polls it (keep its step kinds in step with `SetupStepKind`). Identities: the *operator* (app MI deployed, the local sign-in locally) does pool work; the *user* (Easy Auth's `X-MS-TOKEN-AAD-*` token deployed, the operator locally) runs fixes; the gateway's own MI calls Foundry. `credentials.py` (`LocalCredential`) is the local credential: the app's own sign-in (browser, or device code), then Azure CLI, azd and Azure PowerShell; app sign-ins are remembered through MSAL's encrypted cache plus `backend/.pool-manager-auth.json`, never plaintext. Locally, `config.system_trust` makes the lifespan inject `truststore`.
- `sessions.py`, `entra.py`: the frozen public app; only kept type-checking.

**Invariants to preserve when changing service logic:**
- Deploying on AKS also uses the user's own rights and grants them *Azure Kubernetes Service RBAC Cluster Admin* on the new cluster (Entra ID with Azure RBAC, no local accounts). The secrets are made once, kept in `SecretStore` under `aks-install:<cluster id>` before the deployment is PUT, and reach the cluster only as files in Run Command's context; the install script creates Kubernetes secrets only when missing, so re-running it (`retry_install`, or after a restart) never rotates them, and it never prints them. Once LiteLLM answers, only the master key stays, under the gateway's URL. From then on the cluster is the user's: the app never changes it (no upgrades, scaling or helm), only manages pools in LiteLLM, and shows maintenance commands (`frontend/src/aks-maintenance.ts`). Deleting it is as for Container Apps, with the cluster in `_DELETE_ORDER` beside the environment (not waited for) and its stored keys forgotten.
- Deploying a gateway (local setup only) uses the signed-in user's own rights. It refuses a name whose Container App exists or whose deployment is running or done, registers the providers the template needs, creates a missing resource group (tagged `managed-by`) and never changes an existing resource group or gateway. Every resource carries `managed-by: ai-gateway-pool` and `ai-gateway: <name>`. The secrets are generated once, by the backend, for that deployment: a gateway is never redeployed, because a new salt key would make stored member keys unreadable.
- Deleting a gateway (local setup only, `TargetChooser.delete`) is limited to gateways carrying that `managed-by` tag, needs the name typed again (checked by the backend, not just the UI), deletes only the resources tagged `ai-gateway: <name>` (Container App first, then its environment, then the rest) and never the resource group. There is no soft-delete: its database (pools, keys, spend) is gone, and the dialog says so. Deleting the current gateway clears `backend/.pool-manager.json`.
- Connecting an external gateway checks readiness, the database and the master key against the gateway before saving; the key goes to `SecretStore`, never the state file. Disconnecting forgets the key and doesn't touch the gateway.
- LiteLLM has no ETags. `PoolView.etag` is the hash of the pool's rows, and a save re-reads and compares it (409 on mismatch); a create sends no ETag and fails if the pool or an alias of that name exists. Writes go create → update → delete, so a pool never runs empty mid-save. This is best-effort, not atomic; a failure reports what was already done.
- Rows this app didn't write (no `MANAGED_MARKER` in `model_info.pool_manager`) are shown read-only and never changed or deleted. Model groups or members whose IDs start with a protected prefix (`POOL_MANAGER_PROTECTED_PREFIXES`) are read-only too.
- Every pool save runs `model_check.py`; members whose model can't be read fail. `POST /api/pools/model-check` is the read-only version the editor uses. `POST /api/pools/{id}/preview` returns the current and proposed YAML without writing.
- The cooldown (`PoolWrite.circuit_breaker`: `allowed_fails`, `cooldown_seconds`), `retries` and `timeout_seconds` are pool settings written to every row of the pool. `frontend/src/pool-breaker.ts` holds the defaults the UI starts from.
- Members are managed inside their pool; there is no backends page. Imported deployments wait in memory as pending members until a pool uses them, so imports always land in a pool. When a save drops members, or a pool goes, their rows go with it, and `_delete_unused_credentials` deletes the API-key credentials no row uses any more (failures logged, not raised).
- Aliases are `router_settings.model_group_alias` entries, replaced as a whole through `/config/update`. An alias may not shadow a pool ID or another alias. The aliases this app added are recorded in the pool's rows (`pool_manager.pool.aliases`) and excluded from the ETag.
- Removing a pool, and the gateway-wide cleanup, go through a read-only plan (`GET /pools/{id}/removal`, `GET /cleanup`) and then `POST` the plan the user reviewed (`RemovalConfirm`; cleanup also needs the gateway name typed again). `_remove` recomputes the plan and refuses anything the user didn't see. It removes aliases first (this app's are deleted, others pointing at the pool are unbound), then the pool's test keys, then the rows. Cleanup takes only pools this app created and leaves the gateway itself.
- Virtual keys: LiteLLM keeps only a hash, so a key is shown once, when created, and never stored or logged by this app. The only key this app writes is one test key per pool (alias `<id_prefix>test-<pool>`, `metadata.pool_manager.pool`, `models` = the pool's names); creating it again deletes the old one first (`/key/regenerate` is Enterprise-only). The test call only goes to the gateway's own `/v1` (HTTPS unless running locally), only with a model name of the pool, and returns a filtered set of response headers (no cookies, no cost headers); `x-litellm-model-id` says which member answered.
- Deploying a model runs with the user's own ARM token (`require_user`), never the app identity. Only accounts the discovery scan finds take a deployment; the model, version, deployment type and capacity are checked against that account's `models` list, and an existing deployment name is never replaced. Only OpenAI-format models and the pay-per-token types (GlobalStandard, DataZoneStandard, Standard) are offered; fine-tune SKUs are skipped.
- Setup fixes run with the **user's** token, never the app identity, and the app identity never gets `roleAssignments/write`. Grants are limited to *Cognitive Services OpenAI User* for the gateway's managed identity on accounts that are pool members or discovered (`grant_foundry_access` refuses others), with deterministic assignment names so retries are idempotent. Fix endpoints need the CSRF header and sign-in but not the owners list, because Azure itself authorizes them.

**Tests.** `backend/tests/test_app.py` holds the shared client (`_client`, `seed`, `import_members`, `pool_body`, `create_pool`) that drives the real app through `TestClient` with `ArmClient` wired to `tests/fake_azure.py`, and `GatewayConnection` to `tests/fake_litellm.py`. `fake_litellm.py` is an in-memory LiteLLM admin and inference API behind `httpx.MockTransport` (rows, router settings, keys scoped by `models`, credentials, `failing` rows, readiness, recorded requests; `MASTER_KEY`). `fake_azure.py` is ARM and the APIs next to it: the gateway's Container App and `listSecrets` (`add_gateway`), ARM deployments (`finish_deployment`), tenants, subscriptions, resource groups, providers, effective permissions per caller and scope (`allow()`; a caller without entries has full access), role assignments and definitions (`grant_openai_user`), Foundry accounts, deployments, models and capacities, Azure Monitor metrics (`add_metric`), Cost Management (`costs` by gateway tag), Retail Prices, Log Analytics queries (`log_rows`, `log_queries`, `logs_forbidden`), and for AKS: clusters (`add_aks_gateway`, also created by `finish_deployment` for the AKS template), Run Command (`run_commands`, `command_results`, `run_command_polls`, `run_command_exit`), DNS labels (`dns_taken`), VM SKUs and quota (`vm_restricted`, `vcpus_free`). It maps bearer tokens to callers (`callers`). When you add an ARM or LiteLLM call, extend the fake to match. `test_pools.py` covers pools, members, aliases, keys, the test call and removal; `test_setup.py` the wizard in local and deployed modes; `test_target.py` choosing, deploying, connecting and deleting gateways; `test_aks.py` the AKS path (preflight refusals, the phases, the Run Command body and its files, retry with the same keys, the hand-over, choosing and deleting an AKS gateway, what the install never prints); `test_metrics.py` and `test_cost.py` the Monitor tab and the cost panel. `tests/conftest.py` makes any test that reaches the real ARM factories or the real `SecretStore` in `deps.py` fail, because a missed override would otherwise sign in with the developer's own Azure identity.

**Frontend** (`frontend/src/`): TanStack Query. The query definitions and the fetch wrapper are in `api.ts`. `main.tsx` first runs `session.ts`'s `startSession` (reads `/api/config`). There are two tabs (pools, deployments) in `app.tsx`, kept in `?tab=`. `components/gateway-picker.tsx` is the gateway step: the list, **Deploy a gateway** (the ACA/AKS questionnaire, with the pure recommendation in `gateway-choice.ts`, then the Container Apps form and its deploy progress, or the AKS files), **Connect a gateway**, and `DeleteGatewayDialog` (shared with `components/service-panel.tsx`, behind the gateway name in the top bar, which also has the cost and the cleanup). A pool's members, including custom endpoints (`components/member-backend-dialog.tsx`), and its cooldown, retries and timeout (`components/pool-breaker-settings.tsx`) are edited inside the pool editor (`components/pool-editor.tsx`). Its Test call tab has the endpoint and aliases (`components/pool-endpoint.tsx`, with the LiteLLM YAML view in `components/config-viewer.tsx` and the diff in the pure `config-diff.ts`), the call guide (`components/call-guide.tsx`, snippets in the pure `call-snippets.ts`) the test call (`components/api-tester.tsx`, diagnosis and served-by in the pure `api-test.ts`) and the load test (`components/benchmark.tsx`, a call-guide step that reuses the Monitor tab's chart pieces exported from `pool-monitor.tsx`; presets, estimate, verdict, chart buckets, exports and the terminal command in the pure `benchmark.ts`). The Routing tab simulates LiteLLM's routing (pure `routing-sim.ts`). **Infra.** `infra/gateway/litellm-aca.bicep` is the gateway the app deploys: Log Analytics and Application Insights, a user-assigned identity (the gateway's Foundry identity), PostgreSQL Flexible Server (password auth, Azure services firewall rule), Azure Managed Redis in production, a Container Apps environment and the Container App: LiteLLM on port 4000 with startup/liveness/readiness probes and an OpenTelemetry Collector sidecar (azuremonitor exporter, keeps only model-call spans), the config as a secret volume at `/app/config`. GA Container Apps (`2025-01-01`) has no managed OpenTelemetry agent, hence the sidecar. `infra/main.bicep` hosts the manager: App Service with Easy Auth for an **existing** gateway (`gatewayName`, `gatewayResourceGroup`, `gatewaySubscriptionId`, or `gatewayUrl` + `gatewayMasterKey` for a gateway elsewhere). It never creates or changes the gateway. `enableDelegatedAzureAccess` (off by default, because sign-in breaks until the app registration steps in README are done) adds the ARM `user_impersonation` scope to Easy Auth and a user-assigned identity used as its federated credential. `modules/gateway-rbac.bicep` gives the app identity a custom role (`AI Gateway Pool Manager`: `containerApps/read`, `containerApps/listSecrets/action`, `permissions/read`, App Insights component and logs read) on the Container App and its App Insights component only. `modules/discovery-rbac.bicep` (`AI Gateway Pool Deployment Reader`) gives read-only Cognitive Services access per discovery subscription and has no `listKeys`. The role names are what `access.py` looks up. If the app starts calling a new ARM action, add it to the matching custom role.
